核心哲学:harness 没有 agent 聪明

系统被严格切成两类东西。任何"用关键词 / 正则 / 预先算好的分析去替 agent 二次判断"的诱惑,都删掉。
▶ 归 AGENT(科研判断)
  • idea 平不平庸
  • 项目做完没
  • 基线够不够强
  • 为什么慢 / 瓶颈在哪 / 怎么修
  • 失败是不是可修的 skill_gap
→ L1 engineer 干活 · L2 reviewer 验收 · L4 planner 排活
▶ 归 HARNESS(领域无关的笨管道)
  • 预算 / 调度 / 原子 claim
  • 持久化 / journal / checkpoint
  • 结构化 I/O(JSON schema)
  • 反 livelock / 反 amnesia 护栏
  • 反造假护栏(唯一正当的硬规则)
→ 不读 agent 输出去二次判断、不预先嚼结论
三条推论:① 唯一正当的"硬规则"是反造假护栏(真 benchmark、不重复灌水、留审计、随机化防 hack); ② reviewer 是项目完成与否的唯一事实来源——没有独立 validator、没有硬编码完成门; ③ 给 agent 真访问(自测带宽 / 自跑 torch.compile / 自 profile / 自上网),operator 提供能力而非结论。
I

系统总览

总体架构与角色分层:L4 Planner / L1 Engineer / L2 Reviewer + "harness 没有 agent 聪明"

两层嵌套的 agent harness:外层 LifeSupervisor 管 backlog/预算/调度并调用 L4 Planner 排活,内层 SkillLoop 跑 L1 Engineer→L2 Reviewer 的 round-loop;所有"科研判断"归三个 codex agent,harness 只做领域无关的笨管道。

三层 agent:L1 engineer / L2 reviewer / L4 planner(L3 critic 已删)harness 笨管道 vs agent 科研判断 的强制分工reviewer 是完成与否的唯一事实来源(无独立 validator)round-loop:engineer→checks→reviewer 的 done/continue/blocked 裁决backlog 原子 claim_next(CAS)+ LifeBudget 预算门反 amnesia:session roll(shift_round_limit)+ CheckpointState 跨 session 交接结构化 scope 透传(bounded/final_submission),不从 prose 猜

它到底怎么转的

  • 入口与路由:CLI(argus_skill/apps/cli.py)经 _life_repl 的 _CodexSkillLoopRunner 或 daemon/life_worker.py 起一个 LifeSupervisor;operator 在 REPL 敲的自由文本由 life/router.py 的 classify_is_conversational(text, run_exec) 做一次低成本模型调用分流——只有模型精确回 'CHAT' 才走 build_chat_prompt 闲聊快路径,其余(TASK/模糊/空/异常)一律走完整 mission pipeline。这是'删掉关键词正则、把判断交给模型'的样板,且只对人类自由文本生效,planner/backlog/daemon 任务从不被二次分类。
  • L4 外层调度:LifeSupervisor.run()/tick()(life/supervisor/_core.py)从 backlog.jsonl 用 Backlog.claim_next() 做原子 CAS(pending→running)claim 一个 BacklogItem,先过 LifeBudget.can_start() 的每日预算门(life/supervisor/_config.py),再调 _run_one(item)→ self.runner.execute(MissionExecutor) 跑一个 mission,完事写 journal。backlog 空且 continuous 模式时进 _plan_next_work() 找 L4 planner 续活。
  • L4 Planner:Planner.plan_next()(argus_skill/planner/planner.py)自带 shell 访问,自己 find/ls、跑 pytest/ruff 评估项目,返回 PlannerVerdict——要么 project_done=True(new_tasks 必须为 []),要么给一批 TaskSpec(title/objective/impact_score 0-5/impact_area/scope)。parser 只收 impact_score>=MIN_PLANNER_IMPACT_SCORE(=4) 的高价值任务;waiting=True 是一等公民的'在等外部长跑、无新活'的空闲态,不是 error 也不是 make-work。
  • 完成判定的唯一事实来源是 L2 reviewer,不是 harness:当 full_emnlp_gate=True 且 planner 报 project_done 但 journal 里没有一条被 reviewer 认证(final_submission_certified=True,由 _journal_has_full_emnlp_gate_success() 查)的整链通过记录时,_plan_next_work 用 dataclasses.replace 把 planner 的裁决直接替换成一个 scope=final_submission 的 'Prove final submission readiness' 任务(_core.py:2674-2713),交回 L2 做 full-pipeline 整链认证——harness 绝不自己判'做完了'。
  • 单 mission 核心:SkillLoop.run()(argus_skill/loop.py)流程 = engineer_mission.match(skill 匹配)→ miss 且 distill_on_miss 时用 Distiller 在线蒸馏新 skill(复用 engineer backend,没有独立 scientist agent)→ SupervisedEngineer.run。_build_engineer_prompt 负责把 vertical banner、ground-truth mandate、skill playbook、原始 operator 请求(immutable anchor)、stage checklist、turn-discipline、强制的 '## Verification (verbatim)' 输出块拼成 L1 prompt。
  • L1 round-loop:SupervisedEngineer.run()(argus_skill/engineer/runner.py)每轮 = engineer turn → run_checks(可选 acceptance shell 命令)→ Reviewer.evaluate;done 即停,continue 把 reviewer 的 next_action 注入下一轮 prompt,blocked 停并上抛原因。Codex thread 跨轮 resume 续接(round N+1 复用 round N 的 thread_id),seed_thread_id 让上层跨 mission 续线程。
  • L2 Reviewer:Reviewer.evaluate()(argus_skill/engineer/reviewer.py)每轮一次、跨轮无状态,自带 shell 能自读 artifact/跑检查,产出结构化 ReviewDecision(reviewer_schema.json):status∈{done,continue,blocked}、confidence、next_action、planner_report.forward_progress、failure_cause、mission_lesson、checkpoint。academic-paper-peer-review-benchmark.md 是否注入按结构化 stage/scope 判断(is_final_submission 即 scope=='final_submission',或 stage∈{review,submission}),不再扫 objective/evidence 里的关键词。
  • verdict→终态翻译与反 livelock:runner 把 review.status 翻成 LoopStatus(runner.py:1482 起)——done 且 checks 全过→done;blocked→blocked;engineer 连续 no_progress_threshold(=2) 轮无有效输出 或 reviewer 显式 forward_progress=false 累计达 stall_threshold(=8)→no_progress;跑到 hard_escalate_rounds(=24) 还在 continue→强制 blocked 让 planner 重规划。反 amnesia:每 shift_round_limit(=8) 轮或 thread 超 thread_token_limit(=4M token) 主动 roll 掉 session,用 CheckpointState(engineer/checkpoint.py)做跨 session 的小而硬上限的工作记忆交接。
  • 失败学习只信 reviewer 的归因:SkillLoop._evolve_skill_from_failure 仅当 status∈_REVISABLE_FAILURE_STATUSES({blocked,max_rounds,no_progress}) 且 _find_reviewer_lesson 找到 reviewer 标的 failure_cause=='skill_gap'+非空 mission_lesson 时才去 optimize/create skill;没有可修的 skill_gap 就什么都不学(不从原始日志臆造教训)——再次体现'IF 由 agent 判,harness 只路由'。

为什么重要

这是 Argus 的中枢,直接体现 operator 的头号设计哲学——"harness 没有 agent 聪明"。它把系统切成两类:科研判断(idea 平不平庸、做完没、基线够不够强、失败是不是可修的 skill_gap)全部归三个 codex agent(L1 engineer 干活 / L2 reviewer 验收 / L4 planner 排活),harness 只做领域无关、可证伪的笨管道(原子 claim、每日/单任务预算、journal 持久化、结构化 I/O、反 livelock/反 amnesia 护栏)。对标 Recursive 那类 pipeline:它最关键的反作弊取舍是"没有独立 validator、没有硬编码完成门"——项目算不算完成只由 L2 reviewer 对 full-pipeline checklist 的整链认证决定(planner 误报 project_done 会被强制改派回 reviewer 认证),从架构上杜绝了 harness 用关键词/正则替 agent 报喜报早。对新同事的意义:想改"何时算完成/还差啥派啥"就改 reviewer checklist 和 supervisor 的改派分支,绝不要在 harness 里加关键词判断,否则 harness 就成了天花板。

⚠ 现状 / 局限(诚实标注)
  • 模型默认值文档与代码不一致:README/CLAUDE.md 说三个 agent 默认 gpt-5.4,但 loop.py 的 SkillLoopConfig 里 engineer/scientist 默认字面量是 'gpt-5.5'(reviewer/matcher 默认跟随 engineer)。生产实际 model 由 _life_repl 的 _CodexSkillLoopRunner 在运行时组装注入,这两份 dataclass 默认值更像兜底/死默认,别当权威读数。
  • L3 critic 逐轮打磨层已整体移除(README、AGENTS.md、planner.py 顶部均注明),现在只有 L1/L2/L4 三层;凡看到旧代码/文档提到 critic 多半是历史残留,验收完全由 L2 reviewer 承担。
  • team/ 多 agent teammate 编排是较新的、平行于核心三角色主循环的可选路径:它自述只是 dumb pipe(roster/mailbox/task_board/worktree 隔离),'是否组队、怎么拆分'全在 engineer skill 里。核心 SkillLoop(loop.py)主循环并不经过 team/——onboarding 时别把它和 L1/L2/L4 主循环混为一谈;其实际接线程度我未逐行核到,标注为不确定。
  • checkpoint 跨 mission 持久化未默认开启:SkillLoopConfig.checkpoint_path 默认 None=mission 内内存级(AGENTS.md 亦注明当前 loop.py 实际是内存级),只够修单 mission 内的 amnesia loop;要跨 mission/重启续接需上层显式传 project-state 路径。
  • 完成判定几乎完全压在 L2 reviewer 上:check_commands 默认空([]),很多论文 stage 没有可跑的 acceptance shell 命令,又没有独立 validator/硬编码门兜底(这是设计选择)。代价是 reviewer 一旦误判,唯一防线即失效——这正是 operator 反复强调'reviewer 是事实来源'同时也是单点的地方。
  • 反 livelock/反 amnesia 的阈值(stall=8、hard_escalate=24、shift=8、token=4M)按代码注释是依据实测病理(观测到 17-19 轮空转、5-7M token 进入有损压缩 amnesia 区)经验调的启发式护栏,不是理论最优,可能随负载需要再调。

Reviewer 即真相:项目完成与否的唯一事实来源

L2 reviewer 子 agent 每轮判一次 done/continue/blocked,是项目是否完成的唯一裁决者;没有独立 validator、没有硬编码完成门——harness 只做"跑 check + 把真实报错回流给 engineer"这种领域无关的笨管道。

L2 reviewer 单点裁决 (done/continue/blocked)acceptance-check 红→强制降级 done (_coerce_review_for_failed_checks)真实 check 报错回流 (failed_check_diagnostics, d51fa8b)fail-soft 解析:坏输出退回 continue 绝不假 donereviewer 兼任记忆审计员 (checkpoint cap)planner_report.forward_progress 语义停滞(只数显式 False)

它到底怎么转的

  • 每轮一次裁决,无状态:Reviewer.evaluate(reviewer.py:132)把 objective/engineer 摘要/check 结果/prior checkpoint 拼成 prompt,经 RunnerBackend.run_exec(run_label="reviewer", output_schema_path=reviewer_schema.json)调一次 L2 子 agent,返回 ReviewDecision。类注释明写 'One reviewer call per round. Stateless across rounds.'(reviewer.py:118)——reviewer 跨轮唯一记忆是它自己写的 checkpoint 和上一轮 review 摘要。
  • done 由 reviewer 说了算,无独立 validator:SupervisedEngineer._classify(runner.py:1469)只在 review.status=='done' 且(无 check 或 all_checks_passed)时才回 'done'。prompt 里 final_submission_block(reviewer.py:~529)直说 'You are the single source of truth for project completion — there is no separate validator',且注释标注此块 '替代了已退役的硬编码 EMNLP validators'。
  • 反作弊硬门:check 红就不准 done。_coerce_review_for_failed_checks(runner.py:1695)在裁决后无条件执行——只要有 CheckResult.passed==False,reviewer 的 'done' 会被强制降级成 'continue'(reason 改成 'Acceptance checks failed... cannot be done')。这是 harness 唯一正当的机械护栏:check 失败覆盖一切自我报喜。
  • check 是领域无关的笨管道:run_checks(checks.py:11)把 supervised_config.check_commands 当 subprocess 在 workdir 跑,产出 CheckResult(command, exit_code, passed=returncode==0, output_tail);尾部截到 CHECK_OUTPUT_TAIL_CHARS=60000(checks.py:8)。summarize_checks/all_checks_passed 把结果喂给 reviewer prompt 的 'Acceptance check results' 段。
  • d51fa8b 的核心:真实报错回流给 engineer。failed_check_diagnostics(runner.py:1662)把每条失败 check 的字面 output_tail(取末尾、默认 max_chars=2600、地板 400)拼成 '## Acceptance-check output — the REAL error' 块;runner.py:1385-1388 把它追加到 last_next_action,再由 engineer_prompt_builder(last_next_action)(runner.py:913)注入下一轮 engineer。修复前 engineer 只拿 reviewer.next_action 的转述,看不到编译错误/traceback/数值 mismatch,被迫盲改盲回滚。
  • 解析永远 fail-soft,绝不假 done:parse_decision_text(reviewer.py:979)+_find_decision_in_messages 从 reviewer 消息里抠 JSON;status 只认 done/continue/blocked(_parse_status:1173)。输出非法 JSON、backend 空输出、runner 抛异常,evaluate 一律回 'continue' 或 'blocked'(confidence=0.0),并显式注释 '不要当成 engineer 完成或失败的证据'(reviewer.py:215-219)——错误从不会被误判成 done。
  • harness 不二次猜裁决:evaluate 末尾注释 'The L2 reviewer's verdict is authoritative — the harness must not second-guess it with keyword heuristics on the engineer's summary'(reviewer.py:256-261),直接 return parsed。是否重跑命令、是否凭一句角色确认就放行,全是 reviewer prompt 的职责(prompt 反复要求它自己跑命令拿 ground truth),不靠 harness 后置正则过滤。
  • planner_report.forward_progress 驱动语义停滞检测,但只数显式 False:runner.py:1311-1332 只有 review.status=='continue' 且 raw_forward_progress is False 才 semantic_stall_streak++;_parse_planner_report(reviewer.py:1042)让 done 轮默认 True、非 done 轮缺字段为 None(UNKNOWN)而非 False。设计意图(注释)是不让 reviewer/schema 抖动误杀健康长任务,也不惩罚'诚实测了但回退'的大胆实验。

Compaction 与 Session 交接:用小而精的 curated 检查点替代海量原始历史

长任务里不让 Codex 自己做有损 auto-compaction,而是结构性地把每段 session 做短,只把一个硬上限的 curated 工作记忆(checkpoint,含 env_facts/active_line)干净交接给下一段;另有一条同名但不同事的"技能库去重 compaction"和"过程蒸馏"支线。

curated working-memory checkpoint(硬上限交接)proactive session roll(shift_round_limit / thread_token_limit 两道闸)in-round compaction-thrash 看门狗env_facts / active_line 跨 session 续存regime-jump context reset(cleared_for_jump)engineer HANDOFF → reviewer 审计改写回写闭环

它到底怎么转的

  • 核心反面教材:Codex 把一个 session 跨几百轮 resume 时会反复触发有损 auto-compaction,每次悄悄丢工作状态,直到模型靠反复重读同一批文档来重新定位(checkpoint.py 顶部 docstring 称之为 amnesia loop)。Argus 的解法不是看门狗,而是让 session 结构性短命 + 跨边界只搬一个小的 value-filtered 交接。
  • 交接载体是 CheckpointState 数据类(argus_skill/engineer/checkpoint.py):字段 goal/done/tried_and_failed/maturing/open_blocker/next_step/active_line/env_facts/round。maturing 与 tried_and_failed 刻意分开——一个有前途但首轮没赢的方向不会被一次失败就判死。
  • 硬上限在 Python 里强制(不是只写在 prompt 里):MAX_DONE_ITEMS=8、MAX_TRIED_ITEMS=6、MAX_MATURING_ITEMS=5、MAX_ITEM_CHARS=280、MAX_ENV_FACTS=10 等。_clean_list 还做去重(casefold 去重 + 截断)。上限就是逼作者做删减的 forcing function;from_dict 全程 fail-soft,坏 payload 退化成空字段而不抛异常,绝不打断 round loop。
  • 每轮注入:runner._run_supervised 在循环开头调 checkpoint.render_for_engineer() 把这块 curated 记忆拼到 engineer prompt 最前面(runner.py:917-919),并明确告诉 engineer『这是你对早期轮次的唯一记忆,原始历史被故意丢弃』,同时要求 engineer 在回合结尾产出 HANDOFF: 块(done/tried_failed/maturing/active_line/blocker/next/facts)。
  • Session 主动滚动(roll)是防 auto-compaction 的结构性手段,两道闸:① shift_round_limit(默认 8)按『同一 thread 活了多少轮』滚;② thread_token_limit(默认 4_000_000)按『上一轮上报的 input token 数』滚——后者专治跨多个短 mission 被 resume、rounds_on_thread 一直被重置导致 thread 无界膨胀的情况。触发时只把 current_thread_id 置 None,下一轮开全新 session,仅靠 checkpoint 块重新起步(runner.py:960-1014)。
  • 回合内 compaction-thrash 看门狗:_EffectiveProgressWatchdog 统计该 Codex session 写出的 'compacted' 事件(_CODEX_COMPACTION_EVENT_TYPE),一回合内累计 >= round_compaction_limit(默认 3)就用 'compaction thrash' 这条 fatal_error 打断该回合(runner.py:517-528),按可恢复错误处理,滚到新的 checkpoint-seeded session。fatal_error_looks_like_compaction_thrash 负责识别。
  • 交接回写闭环:runner 把 checkpoint.to_dict() 作为 prior_checkpoint 传给 reviewer.evaluate(runner.py:1285);reviewer 是『记忆审计员』,从 prior_checkpoint + engineer 的 HANDOFF 块亲自 VALIDATE 并改写出下一版 checkpoint(reviewer.py:752-810),经 _parse_checkpoint 落到 ReviewDecision.checkpoint(core/models.py:145);runner 再 CheckpointState.from_dict(...).stamped(round_no).save_checkpoint 持久化(runner.py:1336-1339),空/坏则保留旧的不清空。
  • env_facts 的续命:它是 durable 的环境/基础设施事实(路径、访问端点、版本、谁短暂谁持久),和别的字段一样受硬上限 curation,目的是让 successor 不必每轮重新读/重新发现 setup。reviewer prompt 明确要求『carry prior env_facts forward and add newly established ones』。
  • 与 meta 层联动的 context reset:每段 session 开头若 consume_jump_pending(meta/ledger.py)为真(planner 召集了 regime jump),就调 checkpoint.cleared_for_jump()——丢掉饱和的局部轨迹(active_line/maturing/next_step),但保留 goal/done/env_facts/tried_and_failed(真死路仍然死),让新 regime 干净开局而不重新锚定在冻结的 basin 上(runner.py:894-895、checkpoint.py:327-351)。
  • 同名不同事的支线一:scientist/compactor.py 是『技能库去重 compaction』,不是上下文压缩。它按结构感知相似度(0.45*title+0.15*description+0.15*when_to_use+0.25*category,阈值 0.55)把近重复 playbook 聚类,每簇留 version*(1+history) 最强的一个、archive 其余,纯为压住 matcher 每次匹配的 token 成本;v1 故意不做 LLM 合并。
  • 同名不同事的支线二:life/process_distill.py + process_metacritic.py 是『过程自蒸馏』。前者只读 events.jsonl 抽出量化过程账本(checks 通过率、stall、forward_progress 矛盾等),emit 任何 actionable;后者按 supervisor cadence(默认每 12 个 mission)跑一次只读 meta-critic,产出 status='shadow' 的过程教训,从不自动应用,apply 路径 operator-gated。

为什么重要

这是 Argus『永久不过滤的记忆是毒药』哲学最直接的落地:它不信任 Codex 后端那套有损 auto-compaction(会丢工作状态、逼模型反复重读 = amnesia loop),而是从结构上把每段 session 做短,只跨边界搬运一个硬上限的 curated 工作记忆。两个设计取舍很能说明它的价值观:① 上限在 Python 里强制而非只写在 prompt 里——因为一个啰嗦的 reviewer 哪怕无视 prompt 也不能把毒重新长回来,删减是『主动解药』而非有损;② 科研判断(哪条 active_line 值得续、哪个是真死路、env_fact 是否可信)全归 reviewer/meta 这些 agent,harness 只做去重/截断/fail-soft 这类领域无关的笨管道,严格守住『harness 没有 agent 聪明』的分工。active_line + env_facts 的跨 session 续存,正是让一条大胆方向能跨轮累积、而不是每轮被打回 global-best floor 重新发明的关键机制,直接对应 operator 反复强调的『别让 agent 走贪心小步、要敢迈大步』。

⚠ 现状 / 局限(诚实标注)
  • 命名陷阱(诚实第一条):本子系统标题叫 compaction-handoff,但 5 个起点文件里其实混着三件不同的事——(a) 真正的『上下文压缩 + session 交接』= checkpoint.py + runner 的 roll 逻辑;(b) compactor.py 是『技能库去重 compaction』,跟上下文压缩毫无关系,只是同名;(c) distiller.py / process_distill.py 是『技能/过程蒸馏』另一条线。给新同事讲时必须先把这三者拆清,否则会被名字误导。
  • checkpoint 的质量完全依赖 reviewer(LLM)诚实地从 engineer 的 HANDOFF 校验改写;Python 层只能做截断/去重/fail-soft,无法验证条目真假——若 reviewer 把未验证的自述写进 done,harness 不会拦。这是设计上『reviewer 是事实来源』的必然代价。
  • Codex 的 auto-compaction 是后端自己的有损行为,Argus 控制不了它,只能『绕开』(主动滚 + checkpoint 续命)。4M/8 轮/3 次这些阈值是启发式(注释自陈 4M『sits between normal operation and the bloat zone』),不是实测保证的安全线,换模型/换上下文窗口可能要重调。
  • compactor.py 的去重默认 dry-run,需 --apply 才真 archive;v1 故意不做 LLM 合并(docstring 自陈 v2 才考虑 --smart 的 scientist-mediated merge),所以它只是『挑最强留一个、归档其余』,不会产出融合后的新 playbook。
  • process_distill/process_metacritic 整条是 shadow-only:lesson 一律 status='shadow',真正的 overlay/counterfactual-replay/A-B apply 路径在包外的 self_improving/ 且 operator-gated,当前没有任何自动应用闭环——即它能『发现』过程病灶但不会自己改自己。
  • cleared_for_jump 的触发依赖 meta/ledger 的 consume_jump_pending,整段被 try/except 包住 fail-soft;若 meta 层没产 jump 标志,这条 context-reset 路径就静默不发生,常态下并不频繁触发。
  • checkpoint 续存是 fail-soft 设计:load/save 遇 OSError/ValueError 直接退化成空或静默不写,优先保证『绝不打断 round loop』——代价是磁盘写失败时记忆可能悄悄丢一轮,日志里才看得到。

自进化与破局

自进化:从自己的失败里"看出"缺口,但只检测、不替 agent 决策

operator 点名必含

每个 mission 跑完后,harness 用纯正则/计数的"笨管道"从轨迹里扫出三类信号(缺工具 A、复发 infra 失败 B、过程病理 C),写成 journal advisory 交给 reviewer/planner 自己判断;真要铸新 skill 必须过执行型 held-out fixture 闸,LLM 永不靠"读"来判 skill 好坏。

结构检测与 agent 判断的切分missing-tool / recurring-failure / process 三信号journal advisory(只 surface 不 enqueue)held-out fixture 执行闸(不读文本)shadow process lesson + operator-gated apply防递归 mint-skill tag + 不同 mission 去重计数

它到底怎么转的

  • 三条信号挂在同一个 tick 收尾钩子上:supervisor _core.py 里 _run_one(item) 一返回,就依次 try/except 调用 _maybe_journal_self_evolve_advisory(A)、_maybe_journal_recurring_failure_advisory(B)、_maybe_run_process_distiller(C),每个都 fail-soft 包 except,自进化崩了绝不拖垮主 tick(_core.py:760-796)。
  • 信号 A(缺工具)= missing_tool_detector.scan_mission:纯正则扫 agent_messages / check output_tail / fatal_error / events.jsonl,匹配 command not found、ModuleNotFoundError、exit_code==127、以及自述式 我没有这个工具,产出 MissingToolSignal(tool_name, kind, context, evidence)。SelfEvolveAdvisor.maybe_journal_advisory 把每条写成 self_evolve.missing_tool_advisory journal 条目。
  • 信号 B(复发 infra 失败)= failure_signature_detector.scan_failure_signatures:一张刻意很小的 curated 正则表 _PATTERNS(cuda_oom / cuda_device_assert / nccl_dist_error / hf_flash_attn_unavailable / vllm_engine_init_failed / ray_worker_died / image_generation_model_unavailable),其中 generic=True 的 wrapper 症状在同 mission 有更具体签名时被压掉,避免把 OOM 误记成 vLLM 引擎失败。
  • B 的跨 mission 计数在 RecurringFailureAdvisor 里:每个 (mission,signature) 先落一条低噪 self_evolve.failure_observation 计数行(按 tag 幂等),当同一 signature 在回看窗内命中的不同 mission 数(数 mission id tag 的去重集合,防重放灌水)达到 min_recurrence 才升一条可见的 self_evolve.recurring_failure_advisory,并 dedup 不每 tick 重发。
  • A 与 B 都做防递归:source mission 带 MINT_SKILL_TAG=mint-skill 时直接返回空,因为铸 skill 任务本身在装缺失工具时满屏 not-found 噪声,不能反过来再生成新 advisory。两个 advisor 都无状态,所有状态只活在 journal。
  • 关键设计:这些 advisor 只检测、只 journal,绝不 enqueue。docstring 与 mint-skill.md 都写明,值不值得铸 / 是不是打错字 / 是不是已经绕过去了 是 reviewer/planner 的判断;planner 在 continuous cycle 里扫 advisory、过黑名单、批量 enqueue 带 mint-skill tag 的 BacklogItem。
  • 铸新 skill 的唯一闸是执行型 mint_skill_validator.validate_candidate_skill:它从不读 skill 文本(援引 SkillLens:LLM 判 skill 文本比瞎猜还差 46.4%),而是跑 python <slug>_scripts/main.py < case/input,把 stdout 与 expected 比(文本 byte-exact、.json 用 json-equal),ValidatorReport.ok 要求无结构错误、用例数>=MIN_FIXTURE_CASES 且全过;退出码 0/1 经 D1 gate 喂回 reviewer。
  • 信号 C(过程自蒸馏)分两步:process_distill.extract_process_ledger 纯读 events.jsonl,把 reviewer 每轮 emit 的 failure_cause/mission_lesson/process_lesson 与 planner 的 forward_progress、checks pass/fail、stall 量化成 ledger(含 fp_contradiction:planner 说前进了但 review 没 done / checklist 没满 的矛盾计数);aggregate_ledgers 跨项目合并,挑跨>=2 个项目都重学的同一条 lesson 作为系统性过程缺口。
  • C 第二步 process_metacritic.distill_process_lessons 在 process_metacritic_cadence 个 mission 才跑一次只读 LLM 审计(METACRITIC_INSTRUCTION 强约束:只准改 PROCESS,outcome/metric/verifier 冻结),产出的每条 ProcessLesson 一律 status=shadow,persist_lessons 落 life_dir/process_lessons/,自动什么都不 apply;真正的 overlay/replay/seal 应用路径在 repo 根的 self_improving/,operator 持有、在 agent 触不到的 ~/.argus-seal 与 ~/.argus-meta。

用领域无关的"笨计数器"侦测搜索卡死(floor 冻结+多样性塌缩),由 planner LLM 判定并强制切换 optimizer/architecture/data 等大方向,辅以永不清空的 forbidden-directions ledger 与一次性 context reset——detect/judge/enforce 三权分立,严格守住"科研判断归 agent、harness 只做笨管道"的哲学。

反作弊与 Benchmark 完整性护栏（anticheat-integrity）

Argus 唯一正当的"硬规则"层：用结构闸（structural）硬挡造假与溯源断裂，用顾问闸（advisory）只把事实摆给 reviewer，研究质量裁决永不由 harness 代劳。

结构闸 vs 顾问闸（structural/advisory，kind 驱动退出码）证据链 claim→evidence→bundle→BUILD_INFO（F4）污染 bundle 标记 + 历史状态白名单verifier 重跑 = 唯一可信 reward（自报永不算数）实事求是 ground-truth 前置门no-op/重复 condition 检测

它到底怎么转的

  • 两层闸门是整个子系统的骨架（argus_skill/skills/automated_gates.py）：GateResult.kind 把闸分成 structural（反作弊/溯源，失败经 is_blocking / any_blocking_failure 计入退出码、硬挡这一 round）和 advisory（只把数字塞进 reviewer 的 prompt，passed 恒为 True、永不挡）。STAGE_GATES 是 stage→该跑哪些 gate 的映射，GATE_KINDS 是 structural/advisory 的唯一真值源。文件 docstring 直接写明设计哲学并记录历史教训：c6b11d3 曾把研究质量阈值（min_delta=0.02、min_families>=3）硬编进退出码、让 harness 偷偷做质量裁决，已在 review 中被否。
  • 证据链 F4（evidence_chain.py，validate_evidence_chain）：读 paper/claims_to_evidence.tsv，每条 claim 的 evidence_* 列必须落到 (1) 真实存在的 evidence 文件、(2) 带 BUILD_INFO.md 的 bundle 目录（_bundle_root_for 识别 benchmarks/evidence/<bundle> 或 experiments/<run>）、(3) 非污染 bundle。_bundle_is_tainted 扫 BUILD_INFO/PLAN/RESULTS/EXEMPT 里的 _TAINTED_MARKERS（TAINTED / DO NOT CITE）；只有 status ∈ _HISTORICAL_STATUSES（historical_only/broken_current_evidence/removed）的 claim 才准引污染 bundle，否则报 tainted_bundle_cited。这是 draft/analysis 阶段会硬挡的结构闸。
  • 反'假完成'（run_evidence_health.py，validate_run_evidence_health）：summary.tsv 的 n_errored_trials 不统计 verifier 端 LLM 调用失败，所以 _scan_ctrf 递归遍历每个 bundle 的 jobs/raw/**/verifier/ctrf.json 找 raw_status == 'call_failed'，某 bundle 的 call_failed 占比 ≥ MAX_CALL_FAILED_FRACTION(0.25) 就 block。docstring 记真实案例：29 个 ctrf 里 7 个（24%）call_failed，summary.tsv 却对全部 12 个任务报 accepted=True / reward=1。
  • 审计存在性闸（experiment_audit_gate.py，validate_experiment_audit）：结构而非打分——只强制 paper/EXPERIMENT_AUDIT.{md,json} 存在、机器可读、覆盖 REQUIRED_CHECK_KEYS 五项（gt_provenance / score_normalization / result_existence / dead_code / scope）加 eval_type 分类；读 auditor 字段防手改 PASS（可追溯到真实 reviewer 路由），读 integrity_status 但刻意不评判 pass/warn/fail 本身——裁决权归 reviewer。
  • no-op 检测（method_differentiation.py，validate_method_differentiation）：抓'proposed 方法其实和 baseline 一模一样'。diff 两个 condition 的 config_snapshot.json + 聚合 reward：完全相同命令两套标签 = duplicate_condition（analysis 阶段才升 structural 硬挡）；只换 reward 函数名且 reward_mean/frac_reward_zero_std 统计不可区分 = no_op_suspected（永远 advisory，因为 train-reward 等价不证明 held-out 无差，留给 reviewer）。docstring 记真实 CV-GRPO 案例：compute_score_cv = base*confidence，confidence≈1.0 使提案 reward≈vanilla。
  • 实事求是前置门（ground_truth.py，ground_truth_mandate(role)）：给 planner/engineer/reviewer 注入共享 mandate——把写出 research/GROUND_TRUTH.md（GROUND_TRUTH_RELPATH）当 mission 第一交付物且是 GATE，优化/搭建前必须先写实测的目标/现状/binding constraint；每条结论必须追溯到亲自观察，reviewer 不信 handoff、自验（_ROLE_SLANTS）。该模块刻意任务无关，不硬编任何 benchmark/硬件/metric。
  • 反作弊'原则'落在 vertical 清单 prose（verticals/speedrun/stages.py）：setup.heldout_val 明确把'靠编码已知 eval 分布（baking in fixed statistics of the test inputs）而不是真算结果'判为 reward hack / disqualified；role_banner 的 ANTI-CHEAT(HARD) 禁止开 modded-nanogpt 排行榜或本任务已发布最优解（general method 允许，this task's published solution = DISQUALIFYING）。这些是 reviewer 读的清单文字，不是可执行检查。
  • 唯一可信 reward = verifier 重跑：speedrun measure.repeat_mean_metric 与 life/research_profile.py 的 anti-cheat 条款都规定 agent 自报的 'val_bpb:' 行永不算 reward，只有 verifier 在同协议下重跑 frozen scorer 的数才算；自报与 verifier 冲突一律以 verifier 为准。frozen/editable 边界（只能改 solution，harness/scorer/metric/budget byte-identical）由 reviewer 用 hash/git diff 核（setup.solution_self_contained），不是包内自动 gate。
  • 接线（tools/stage_check.py）：调 run_stage_gates(root, stage=...)，遍历结果——structural 失败累加进 structural_block 计入退出码、advisory 只打印 📋 不计；退出码就是这一 round 能否前进的硬信号。CLI _core.py 也走同一入口。

为什么重要

这是 operator 头号要求'绝对诚实'在代码里的落点：唯一正当的硬规则就是反造假护栏。两层闸把'挡 round 的权力'严格限定在结构/溯源造假（断链、引污染 bundle、verifier 调用失败、产物缺失、命令重复的伪 method），而'够不够好/Δ够不够大'这类研究质量判断永远归 agent/reviewer——c6b11d3 把质量阈值塞进退出码即被否，正是这条边界的判例。它服务于复现 Recursive 时的核心承诺：报出来的每个数都能追到真实公开 benchmark + verifier 同协议重跑，不让作弊或抖动刷出来的数冒充结果，也不让 harness 越权替 agent 当大脑。

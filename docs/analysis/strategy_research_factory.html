1.为什么不追 ARIS

ARIS 走的路是 "skill 库 + MCP + 多 host 适配"，他们 25k stars 月发 11 个 release，正面追只会越追越像一个差的 ARIS。

但 ARIS 的定位有一个结构性盲点 —— 它叫 "Auto-claude-code-research-in-sleep"，README 反复说 "wake up to find your paper scored"， 但 ARIS 其实做不到这件事：它需要用户挂着 Claude Code session，host 一关就断； 没有 cost ledger，跑飞了就跑飞了；没有 watchdog，agent 卡住没人知道； 没有 benchmark harness，跑分得用户自己手搓。

这恰好就是 argus-skill 已经做了 70% 的事。所以不该补差距，该把这条路做到极致。

3.5 个 Killer Feature

这五条都满足两个条件：(1) ARIS 结构上做不到 (2) 我们当前 codebase 已经有基础。

F1 多项目并行 backlog

一个 daemon 同时跑 N 个研究项目，每个有独立 backlog、cost ledger、evidence bundle 目录。 argus-skill --project paper-a --objective "..." --continuous 起一个； argus-skill --project paper-b ... 再起一个； 调度器按 token 配额轮转。

argus-skill --status 列所有项目：哪个 running / 哪个 quarantine / 各花了多少钱。

ARIS 为什么做不到：per-session 架构，host 一次只能跑一个工作流。
F2 Weekly Telegram Digest

每周一上午 9 点自动 push：本周哪些项目有进展（合并的 PR / 跑通的实验 / 新 evidence bundle）、 哪些卡住（连续 N 轮 no-progress）、本周花了 $X / 剩余预算 $Y、推荐用户处理的事项（quarantine 项需要人工拆解 / 新发现的实验机会）。

是 inbox 的反向 —— 不是用户 /status 主动查，是 daemon 主动汇报。

ARIS 为什么做不到：没有持续运行的进程，没有可以汇报的"本周"。
F3 Anti-mediocrity Hard Gate

当前 anti-mediocrity 是 reviewer prompt 里的 5 条 checklist，模糊判断。升级成：

  • "基线复现失败" → Python validator 检测 evidence bundle 里有没有至少 1 个 baseline reward > 0 的 trial → 没有则项目 quarantine
  • "改进 < 2%" → 比较 proposed vs strongest baseline 的 reward delta → 不达标则 planner 自动 enqueue "重新设计实验" 任务
  • "benchmark < 3 族" → 扫描 manifest.json 的 dataset_id → 不够则 enqueue "选第 3 个 benchmark"

所有判断走 pipeline_contracts.py Python validator，可以单元测试、可以 CI 检查。

ARIS 为什么做不到：没有 benchmark harness，没有 evidence bundle 概念，"改进 < 2%" 这种判断只能让模型主观看。
F4 Evidence Chain Validator

把 paper/build_*_artifacts.py 那条链强化成硬合约：

  • 论文 main.tex 里每个数字 → 必须在 claims_to_evidence.tsv 里有 claim_id
  • 每个 claim_id → 必须指向 benchmarks/evidence/ 下的 bundle
  • 每个 bundle → 必须有 BUILD_INFO.md（含 git commit / run id / cost / tainted 标志）
  • 断链则 review stage 自动 fail，draft 不能进 submission stage

用户最终交付物是 paper + reviewable bundle，审稿人能一键复跑。

ARIS 为什么做不到：没有 evidence bundle 概念，claim ↔ source 链条不存在。
F5 Project Lifecycle State Machine

项目状态明示化：incubating（idea 阶段）→ running（实验中）→ writing（draft 中）→ quarantined（卡住，待人工）→ done（提交）→ archived。

转移规则是 Python 状态机，不是 prompt：

  • 跑超 14 天没进 writing → 自动 quarantine
  • 预算花到 80% 还没进 review → 自动 quarantine
  • quarantine 后 daemon 不再分配 token，等用户 /resume <id> 或 /archive <id>
ARIS 为什么做不到：per-session 没有"项目"概念，所以也没有项目生命周期。

4.3 阶段路线图

P1 收敛 · 2 周

把不在新方向上的代码砍掉，让 codebase 反映新定位。不写新 feature。

  • 删除 argus_skill/scientist/、argus_skill/critic/、argus_skill/life/iteration_loop.py 相关
  • 合并 argus_skill/mission/ 到 life/supervisor.py
  • 砍掉 builtin_skills/ 里不在主干（auto-research-pipeline / benchmark-runner / draft / review / submission）上的 skill，归到 examples/
  • 重写 README：删 "31 个 skill" 营销，立 "autonomous research factory" 定位
  • 删 paper/figures_tables.md 和 claims_to_evidence.tsv 里所有 tainted bundle 引用
  • 修复 / 删除上一轮 skip 的 11 个 critic-iteration 测试（删除路线）

P2 工厂化 · 3 周

把 daemon 从"跑 1 个 project"扩到"跑 N 个 project"，加 weekly digest。

  • 实现 F1 多项目 backlog：--project ID，每项目独立 ~/.argus-skill/projects/<id>/
  • 调度器按 token 配额轮转，--status 列所有项目
  • 实现 F2 weekly digest：cron 触发 → 聚合每项目状态 → telegram_bot push
  • 实现 F5 项目生命周期：状态机 + 14 天 / 80% 预算自动 quarantine
  • tests：跑 7 天模拟（fake clock）验证 quarantine + digest 正确触发

P3 硬化产出 · 3 周

把"输出 paper draft"做到能交给审稿人的程度。

  • 实现 F3 anti-mediocrity hard gate：基线复现 / Δreward / benchmark 数 三条 Python validator
  • 实现 F4 evidence chain validator：claim ↔ evidence ↔ bundle ↔ BUILD_INFO 四级硬合约
  • 新增 argus-skill --transparency-report <project>：输出该项目的所有 claim → evidence 链 + 所有 tainted 标注
  • 把 transparency report 当成项目交付物的一部分，跟 paper.pdf 一起放在 release/
  • 用一个真项目跑 30 天 end-to-end，验证整套工厂工作

6.不做什么

不做因为
不抄 ARIS 的 81 个 skill很多是 prompt 模板，离开 ARIS 的 workflow 没意义
不写 Rust CLI 对标 ARIS-Code11 个 release/月堆出来的，性价比极低
不做多 IDE 适配（Cursor / Trae / Antigravity / Copilot CLI）我们卖的是 daemon，不是 skill 库，挂到 IDE 反而稀释定位
不接 11 种 providerAzure OpenAI 一档够用，加 OpenAI 直连兜底就行；多 provider 是 ARIS 的卖点不是我们的
不做 MCP servers我们 reviewer 已经是独立 codex 实例，再加一层 MCP 是凭空增加复杂度
不做 community/papers 收录、awesome 列表、营销先把第 1 篇真 paper 跑出来再说
核心赌注： ARIS 的 25k stars 大多数是 "wake up and find your paper scored" 这个故事吸引来的。 但 ARIS 自己做不到这件事。

如果我们能真的做到 —— 一个用户起 3 个项目，3 个月后真的拿到 3 篇带 reviewable evidence 的 paper draft —— 那 25k 用户里的 1% 会迁移过来。 1% × 25k = 250 个高质量用户，比追 81 个 skill 有意义得多。
主要风险： 30 天无人值守跑通的难度被严重低估。当前 codebase 的 watchdog / failed-tool ledger / cost ledger 都是单 mission 级别的， 跨 N 项目 N 天的全局调度 + 故障恢复 + 预算分配是真正的工程挑战。
P2 / P3 各预留 50% buffer。

生成时间 2026-05-29 · 对比对象 wanshuiyin/Auto-claude-code-research-in-sleep（25k+ ⭐，VALSE 2026，HF Daily Paper #1）

一句话结论： ARIS 是 "skill 库 + MCP 网格"——任何 host（Claude Code、Codex、Cursor、Trae、Antigravity、Copilot CLI、OpenClaw）都能挂载，跨模型对抗审稿是它的核心壁垒。 argus-skill 是 "自带 runner 的 Python 包"——能力都被绑死在 codex 后端 + 自家 REPL。 要追的不是 skill 数量，而是 (1) skill 格式可移植化、(2) reviewer 跨模型化、(3) MCP 接入这三件事。

关键洞察： ARIS 把单价值（skill 内容）做厚做扁平；argus-skill 把多价值（runner+supervisor+daemon+reviewer+memory）绑死在 Python 实现上。 这意味着 ARIS 的 skill 任何人能用，我们的 skill 只有跑 argus-skill 的人能用 —— 这是用户基数差的本质。

2. argus-skill 比 ARIS 强的地方

差距分析容易让人觉得"全面落后"，但其实 argus-skill 守住了一块 ARIS 结构上做不到的领地 —— 真正的 7×24 自主执行 + 工程级状态机。下面这些能力 ARIS 没有、或者只能用 prompt 间接模拟：

#能力argus-skill 怎么做ARIS 为什么没有
A1 真守护进程 + 持久 backlog argus_skill/daemon/life_worker.py + life/supervisor.py 是真 Python 进程，argus-skill --daemon 后台 detach；BacklogItem 持久到 ~/.argus-skill/projects/<hash>/ ARIS 名字叫 "research in sleep" 但本质是 skill 库，得让用户挂着 Claude Code session 才能"睡"。退出 host 等于断点
A2 continuous planner 自己长任务 --continuous --objective ... 模式下，backlog 空了 planner 自动生成新任务（带 quarantine 防重复 no-progress 任务） ARIS 每条 workflow 都要用户手动 /auto-research-pipeline xxx 起一次
A3 结构化 ReviewDecision engineer/reviewer.py 返回 ReviewDecision(status, confidence, reason, next_action, completion_summary_markdown, ...) —— Python 类型，可测试可组合 ARIS reviewer 是 "把 Codex 输出当 markdown 解析"，没结构合约
A4 cost ledger + 预算硬上限 core/pricing.py 按 HTTP 计费精确累计；per-mission $30 / daily $180 在 LifeBudget 强制；--status 直接看 cost: $0.00 total ARIS 跨 skill 没有统一 cost ledger，预算靠用户自觉
A5 failed-tool ledger + 重复失败 advisory engineer/failed_tool_ledger.py 跨 round 跨 mission 记录同一工具/命令失败次数；满阈值后在下一轮 prompt 顶部插警告（每工具每 mission 只插一次） ARIS 没有跨 round 失败记忆
A6 effective-progress watchdog runner 检测 session events + 项目文件变化签名，N 秒无进展自动 interrupt（避免 agent 假装在干活） ARIS 没有运行时进度检测，靠 reviewer 事后判
A7 真 validator 是 Python 代码 skills/pipeline_contracts.py 的 validate-full-emnlp 等是 Python 函数 + exit code，能在 CI / shell / reviewer check 里复用 ARIS 的"validator"是 SKILL.md 里的 prompt 自然语言指令，靠模型自己执行 —— 不可单元测试
A8 真 benchmark 跑分基础设施 benchmarks/harbor_adapter.py（harbor adapter）+ benchmarks/validate_results.py，能跑 benchmark 全套 trial 并校验 evidence bundle ARIS 没有自己的 benchmark harness，靠 community 论文里各自手跑
A9 三层 agent 状态机 Planner ↔ Engineer ↔ Reviewer 是分离的 codex 实例，BacklogItem 在三者间显式流转，有 tags = ["planner", "scope:bounded"] 这种可查询字段 ARIS 的"reviewer"其实是 MCP 子进程，没有全局 planner 层；skill 之间是平铺的
A10 Telegram 双向 inbox life/telegram_bot.py：/status /project /stop <id> 手机直接打回 backlog，--notify MSG 反向 push ARIS 有 feishu-bridge 但是单向通知 MCP，不是 inbox 双向
A11 session 恢复 tests/test_session_resume.py 覆盖：daemon 重启后从 BacklogItem 持久化状态续跑，不是从零开始 ARIS 工作流是 stateless skill，崩了得手动重跑
A12 quarantine + no-progress 防呆 planner 检测近 N 个 history 里同 title/objective 已 no-progress 失败过的任务，自动 quarantine 不再 enqueue ARIS 没有"上次这个 prompt 干了等于没干"的记忆，会反复重启同一 skill
A13 1187 测试 + mypy + ruff CI gate Python 包 → 真单元测试覆盖 supervisor / runner / planner / reviewer / packaging / benchmarks 各层 ARIS 主体是 markdown，CI 主要是 release/drift，逻辑层无法 unit test
A14 工程诚信 docs/KNOWN_BUGS.md 明确标注哪些 evidence bundle 因 docker rate-limit / 401 被污染、不可作为 paper 证据 ARIS README 营销密度极高（"VALSE 2026 · HF Daily Paper · 25k stars · 11 release/月"），但实际有多少 reproducible benchmark 不透明
定位差异：
ARIS 卖的是 "我有 81 个 skill + 跨模型审 + 多 host 适配" —— skill 内容厚 + 接入面广。
argus-skill 卖的是 "我能 7×24 自己跑完整流水线，带预算、带 watchdog、带状态恢复" —— 执行可靠性 + 工程化深度。
两条赛道不直接冲突。我们补 P1 是为了"让别人也能用我们的 skill"，但不要为了像 ARIS 而把 daemon/supervisor/ledger 拆掉 —— 那是我们的核心壁垒。

4. 行动计划

分四个阶段，每阶段独立可交付。建议先打 P1 拿到"我们的 skill 任何 host 都能用"的基线能力，再视用户反馈决定 P2/P3。

P1 Skill 可移植化（1 周）

目标：让 argus-skill 的 32 个 builtin skill 能被任何 Claude Code / Codex CLI 用户直接 mount，去掉对自家 runner 的硬依赖。

  • 给 argus_skill/builtin_skills/**/*.md 全部补 ARIS 风格的 YAML frontmatter（name / description / argument-hint / allowed-tools）
  • 把 argus_skill/builtin_skills/ 软链/导出到仓库根 skills/，使 git clone && cp -r skills/ ~/.claude/skills/ 一步可用
  • 新增 --export-builtin-skills DIR 的输出与 ARIS 格式对齐（已有 flag，但内部还在用 router 风格）
  • 测试：写一条 contract test，断言每个 skill 文件有合法 frontmatter（name 非空、description 非空、allowed-tools 是数组或字符串）
  • README 加 "Use as plain skills" 段：复制路径、in Claude Code、in Codex CLI

P2 MCP servers + 跨模型 reviewer（2 周）

目标：reviewer 走 MCP，可换成 Gemini / Claude / Oracle / manual，不再绑死同 codex 实例。

  • 在仓库根新增 mcp-servers/ 目录，复用 ARIS 的 server.py 模板（MIT 兼容许可）
  • 实现 3 个：gemini-review、manual-review（含 ui.html）、image2
  • argus_skill/engineer/reviewer.py 加 REVIEWER_BACKEND env 路由（codex / mcp:gemini-review / mcp:manual-review）
  • 新增 REVIEWER_DIFFICULTY = medium / hard / nightmare 三档（hard = reviewer memory + debate；nightmare = 直接 codex exec 读 repo）
  • 测试：mock MCP server，验证 reviewer.py 正确路由到三种 backend
  • 文档：新增 docs/REVIEWER_BACKENDS.md
风险： MCP 协议本身有 stream/timeout 健壮性坑（ARIS v0.4.10–v0.4.15 的 release notes 里反复在修这些）。 先从 stdio MCP 起步，不要做远程 HTTP MCP server。

P3 内容深化（2 周）

目标：补关键缺失的 skill 和模板，把现有研究流跑得更密。

  • 新建 templates/ 目录，复用 ARIS 的 17 份模板（CN/EN）：EXPERIMENT_PLAN_TEMPLATE / FINDINGS_TEMPLATE / NARRATIVE_REPORT_TEMPLATE / PATENT_CLAIMS_TEMPLATE 等
  • 新增 8 个 ARIS 风格的 skill：
    • citation-audit（第四层 bibliography 审）
    • novelty-check（双线程对抗：找原创性反例）
    • openalex（除 arxiv / S2 外的第三个文献源）
    • kill-argument（双线程对抗审 theory paper）
    • meta-optimize（self-evolution：分析 log → 生成 SKILL.md 补丁）
    • render-html（review report → 单文件 HTML，类似本文档）
    • rebuttal（审稿回应起草）
    • overleaf-sync（双向 Overleaf Git bridge）
  • 新增 argus_skill/research_wiki.py：papers/ideas/experiments/claims 持久化 + 关系图。参考 ARIS 的 tools/research_wiki.py 设计

P4 平台化（4 周以上，按需）

目标：脱离 Azure 锁定，把 argus-skill 推广到其他 host 和 provider。

  • 多 provider 路由：env ARGUS_PROVIDER ∈ {azure, openai, deepseek, kimi, modelscope, dashscope}
  • 多 IDE 适配文档：docs/CURSOR.md / docs/CODEX_CLI.md / docs/COPILOT_CLI.md
  • claude-hooks 模板（templates/claude-hooks/meta_logging.json）
  • Drift CI：监测 argus_skill/builtin_skills/ 与导出 skills/ 不一致时 fail
  • community/ 目录收录用 argus-skill 写出的 paper（如果有）

6. 不建议做的事

  • 不要写 Rust CLI 对标 ARIS-Code。 这是 ARIS 11 个 release/月堆出来的东西，正面拼性价比极低。我们的优势是 Python 生态 + Azure，应该利用而不是丢弃。
  • 不要照搬 81 个 skill。 很多 ARIS skill 是为特定 workflow（W1/W2/.../Wiki/Oracle）服务的，离开那个工作流没意义。挑高频通用的 8 个就够了。
  • 不要为了"看起来像 ARIS"而把 daemon/REPL 拆掉。 7×24 自主跑是 argus-skill 的差异化定位，ARIS 反而做不了（它只是 skill 库）。保住这一条。

7. 决策点

建议优先 P1（一周内） —— 拿到 "我们的 skill 任何 Claude Code 用户都能 mount" 这条基线能力。 然后看一周内有没有外部用户反馈（GitHub stars / issues），再决定 P2 是接 MCP reviewer 还是先做 P3 的 skill 内容。

P1 的具体执行 checklist 可直接交给一个 agent 跑：

1. 列出 argus_skill/builtin_skills/**/*.md 全部文件（~32 个）
2. 给每个文件加 YAML frontmatter（name / description / argument-hint / allowed-tools）
3. 写 tests/test_skill_frontmatter_contract.py 校验
4. 在仓库根新建 skills/ 符号链接到 argus_skill/builtin_skills/
5. README 加 "## 作为 Claude Code skill 使用" 段
6. 在 .github/workflows/ci.yml 新增 frontmatter contract step

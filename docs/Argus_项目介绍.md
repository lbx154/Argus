# Argus — 一个 7×24 不停机、自己做研究的 AI

> **一句话**：给它一个研究目标和这台机器的规则，它就**全天候不间断地自主做研究**——
> 选题、调研、设计实验、在**真实指标**上测量、分析、写代码、产出可复现的结论。
> 研究目标可以是一篇论文、一个要逼近硬件极限的 CUDA kernel、一个要提速的训练脚本、一套要挖掘的量化因子——
> **它们共用同一套原则**。它的本事不在「会写论文」，而在**能把高密度的智能任务一刻不停地执行下去：不空转、不打滑、不卡死。**

*Autonomous Research Generation & Understanding System*

---

## 1. 它是什么

Argus 是一个**完全独立于人、长期自主运行的 research agent（研究智能体）**。你只告诉它两件事——

1. **做什么**（objective，研究目标——一篇论文、一个 CUDA kernel、一个训练脚本、一套量化因子……）；
2. **这台机器的规则**（special prompt：有几张 GPU、数据放哪、调度有什么约束）。

然后它就**自己一直干下去**，没有人在回路里逐步审批。做研究需要的每一个**判断**——idea 平不平庸、
文献查全没、实验做完没、基线够不够强、结论站不站得住——都是 agent 自己下的。

无论目标是论文、kernel、训练脚本还是量化因子，它们**共用同一套原则**：拿一个**诚实的硬指标**，在
**不作弊**的前提下，**连续数天**密集地逼近极限 / 打败一个同等条件下的强基线（见第 5 节）。Argus 的
引擎就是为这种形状的问题造的——**不是为某一个领域**。

但「自主」最难的地方，不是让 agent 做出一个判断，而是让它**连续几天、几千轮地一直产出有效工作**
而不退化。一个长跑的自主 agent 真正会死在三件事上：

- **空转**：明明有活可干，却在原地等一个早有人盯着的长实验，一轮又一轮重复轮询同一个状态文件；
- **打滑**：上下文被反复有损压缩，记忆悄悄丢光，于是反复重读同一批文档、原地空想，看着很忙其实没进展；
- **卡死**：某一步 hang 在一个挂起的调用上、或在一个永远过不了的门前反复打磨，整条流程僵住。

**Argus 的核心工程，就是把这三件事从结构上堵死。** 这才是它和「能跑个 demo 的 research agent」
的本质区别——见第 2 节。

> **诚实说清楚边界**：它现在**不是**「一键拿到 SOTA / 一键被接收的论文」。它是一个**有监督但自主**的
> 研究系统，不保证每个目标都达成（论文不一定中、kernel 不一定摸到 1.0）。但它能做到的是：**给定一个
> 长达数天的研究目标，它会一直密集地、不退化地把它往极限推。**

## 2. 核心承诺：不空转、不打滑、不卡死

这不是口号，是写进代码、带默认值和测试的机制。下面三块，是 Argus 真正的护城河。

### 🟢 不空转 —— 永远有有效工作在跑，不在原地等

- **不替别人盯已经有人盯的活。** 当 agent 起了一个长跑实验（比如一次 RL 训练），那个任务有**自己独立的
  监督进程**在按节奏查健康、能崩溃即停、终态会回报。Argus 会**主动告诉 agent**：「这个 run 自己有人看，
  你不用守着它，去把不依赖它的下游工作往前拉。」（历史上的病灶：一次 RL pilot 累计几百轮，每轮只在
  重读 `status.json`、再写一份监控文件——纯空转。）agent 若确实只剩等待，可以显式说「按它监督进程的
  节奏复查」，框架就**休眠到该 run 到终态再唤醒**，而不是空烧一轮又一轮。
- **待办空了就自动补活。** 永续模式下，规划层（Planner）一旦发现没活干，立刻规划下一批任务——
  **7×24 永不闲置**。
- **可并行的智能体团队。** Argus 内置一套 team 机制：一个协调器维持一个**滚动的 agent 池**，
  多个 teammate 从任务板上并行领活。同一时刻是一**群**智能体在密集推进，而不是一个串行的工人。

### 🟡 不打滑 —— 长跑不失忆，不原地空想

这是长 horizon agent 最隐蔽的杀手。底层模型的会话被一轮轮续接后，会被**自动有损压缩上百次**，
每次都悄悄丢掉一部分工作记忆，最后模型「忘了自己做到哪」，只能反复重读同一批文档来重新定位——
**看着很忙，其实在原地打滑**。（实测：正常工作轮上下文约 200 万 token，而这种「失忆—重读」环会涨到
500–700 万。）

Argus 的解药**不是加个看门狗**，而是从结构上让会话**短命 + 只交接经过筛选的记忆**：

- **一份极小、硬上限的「工作记忆」**（目标 / 已完成 / 试过但失败 / 正在成熟中 / 当前阻塞 / 下一步）。
  上限在代码里强制——**装不下就必须扔掉最没价值的**，「删除」正是解毒剂（地面真相都在磁盘产物里，
  随时可重新召回，所以大胆删是安全的）。
- **由 reviewer 担任「记忆审计员」**：每轮由 engineer 提议一份记忆交接，reviewer 对照实际产物核验后
  落定下一份。
- **会话定期「换班」**：一个会话活满 N 轮（默认 8）就主动丢弃，下一轮从那份小记忆**重新播种一个全新会话**，
  让单会话上下文有界——上百次压缩的失控从根上不可能发生。崩溃 / 跨任务继承一个臃肿会话时，也按
  token 量在第一轮就丢掉重生。

### 🔴 不卡死 —— 僵住能被发现、被打断、被重新分解

- **语义进度看门狗**：盯的不是「挂没挂」，而是「**项目有没有真的在前进**」。一轮在烧时间却没有产生有效
  进展，会被叫停（默认 60 分钟），而不是傻等一个死循环烧到天荒地老。
- **多重停滞护栏**：连续若干轮 engineer 毫无产出 → 退出；reviewer 多次判定「这轮没真进展」→ 当作停滞退出
  （观测到的病灶是 17–19 轮空转）。
- **反活锁升级**：一个任务每轮都有一点边际进展、却永远过不了门，会被升级——到软上限（默认 12 轮）让
  reviewer 判断是不是被外部依赖卡住、到硬上限（默认 24 轮）强制结束为「卡住」，**交回 Planner 重新规划/
  拆解**，并重读 operator 收件箱。
- **团队层硬兜底**：并行池里某个 teammate 卡在一个挂起的调用上（hang 住的 codex/bash/ssh），会被**硬性
  超时杀掉**（默认 10 分钟宽限后 SIGKILL），它的任务心跳变陈旧、协调器自动改派给别人——一个卡住的
  worker 不会拖垮整台机器，也不会让池子停止补员。

> 这一节里没有一条是「靠改 prompt 哄 agent 别偷懒」。全部是**结构性的根因修复**：让空转无处可空、
> 让记忆有界不滑、让僵住可被发现并打断。

## 3. 设计哲学：harness 没有 agent 聪明

为什么上面这些机制都长成「结构性护栏」而不是「替 agent 拿主意」？因为整个系统建立在一句话上：

> **承载它的那套程序（harness），没有 agent 自己聪明。**

所以我们把事情严格分两类，谁也别越界：

| | 谁负责 | 例子 |
|---|---|---|
| **智能判断** | **Agent**（会思考的模型） | idea 平不平庸？这段记忆相不相关？实验做完没？基线够不够强？该不该等这个 run？ |
| **领域无关的笨管道** | **Harness**（承载程序） | 预算/限速、存盘&记忆、调度&守护进程、结构化读写、**防空转/打滑/卡死的执行护栏**、防造假护栏 |

**Harness 只做后者。** 它是一根「又粗又笨的管子」，绝不**用关键词/规则去猜**「这是不是论文任务」
「该不该判完成」「哪段记忆相关」「这个 idea 够不够格」。任何时候只要 harness 开始替 agent 做**智能
判断**，它就成了整个系统的天花板——而它远没有 agent 聪明。

注意第 2 节的护栏**没有违反**这条哲学：它们管的是「**有没有在有效执行**」（领域无关的机械事实——
进度看门狗、上下文大小、心跳是否陈旧），**不是**「这个研究判断对不对」。后者永远归 agent。
「这个 run 该等还是该放」最终也是 agent 自己决定的，护栏只提供准确事实。

直接后果：

- **没有关键词分类器**，没有硬编码的「完成」判定——**完成与否由 reviewer 对照检查清单亲自裁决，
  是唯一事实来源**。
- **记忆是中立的**：只按时间倒序给最近若干条、标「仅供参考」，不替 agent 猜「哪条相关」。
- **唯一正当的「硬规则」是防造假护栏**（见第 7 节）——它约束的是作弊，不是研究选择。
- **入口必须显式配置**：起守护进程前必须同时给齐研究目标 + 至少一条机器规则，缺则直接退出——
  绝不让 agent 在「不知道目标、不知道规则」下空跑或靠猜。

## 4. 怎么工作：四个角色 + 可并行团队 + 笨管道

```
        ┌──────────── Harness（领域无关的笨管道）─────────────┐
        │  预算/限速 · 存盘&记忆 · 调度&守护进程 ·             │
        │  执行护栏（不空转/打滑/卡死）· 防造假护栏            │
        └───────────────────────┬─────────────────────────────┘
                                 │ 喂任务 / 存产物 / 按预算&节奏调度
                                 ▼
                           ┌──────────┐
              操作员 ────▶ │ Manager  │ 前门：闲聊/任务分流；
                           └────┬─────┘ pipeline 阶段转移的唯一权威
                                │ 派发任务
   ┌────────────────────────────┼─────────────────────────────┐
   ▼                            ▼                             ▼
┌─────────┐   任务+经验   ┌──────────┐   产物+检查   ┌──────────┐
│ Planner │─────────────▶│ Engineer │─────────────▶│ Reviewer │
│  规划   │              │  工程    │              │  审稿    │
│  (L4)   │◀─────────────│  (L1)    │◀─────────────│  (L2)    │
│排下一个 │  done 后续派  │查文献/写 │ 通过/继续/    │对照清单  │
│任务/拆解│              │码/跑实验/│ 卡住          │逐条裁决  │
└─────────┘              │写论文    │ (+具体修复指令)│+审计记忆 │
                         └────┬─────┘                └──────────┘
                              │ 可派生
                              ▼
                    ┌───────────────────────┐
                    │ 并行 subagent / team  │
                    │ 各自带独立监督进程，   │
                    │ 长实验自看护、卡住自杀 │
                    └───────────────────────┘
```

四个核心角色都是会思考的模型（基于 OpenAI Codex CLI，默认 `gpt-5.4`，可按角色独立配置 backend/model）：

- **Manager（前门 + 阶段权威）**：操作员的唯一入口——自然语言先由它判断是闲聊还是任务（模型判断，不是关键词），
  闲聊直接答，任务才往下派给 Planner/Engineer/Reviewer。它也是 pipeline 阶段（`current_stage`）转移的**唯一权威**，
  其余三个角色只能建议、不能自己推进阶段。
- **Planner（规划，L4）**：永续模式下待办空了就排新任务；任务卡住时把它拆解重排——**保证机器永远有活、
  且活是可推进的**。
- **Engineer（工程，L1）**：单轮干活，可派生**带独立监督进程的并行 subagent**（如长训练）去后台跑，
  自己继续推进别的工作。
- **Reviewer（审稿，L2）**：逐条审产物给裁决（通过 / 继续+具体该改什么 / 卡住），同时**担任记忆审计员**
  维护那份小工作记忆。**它是「任务/项目算不算完成」的唯一事实来源。**卡住需要操作员定夺时会带一句具体问题，
  操作员直接回复即可续上。

加上一套 **team 池**：协调器维持滚动的 agent 池、多 teammate 从任务板并行领活，并对「池子过度繁殖」
和「卡死的 teammate」做了硬化（进程级精确计数 + 硬超时杀）。另外还有一个可选的 **Curator** 角色，
只在开了并行 team 模式时才跑，负责 skill 池维护和团队排行榜蒸馏。

## 5. 同一套 principle，多种研究问题

**Argus 不是论文系统。** 它的引擎（第 2–4 节那套）是**领域无关**的，适合任何**长程、可度量、且容易作弊**
的研究/优化问题——有一个诚实的真实指标、有一个要在同等条件下打败的强基线、有明确的「作弊捷径」要堵、
需要连续数天密集执行。论文只是其中一种。下面是同一套引擎在驱动的几类研究问题（各自是独立 mission，
共用同一套原则）：

| 研究问题 | 真实指标（越接近极限越好） | 要打败的强基线 | 被护栏堵死的作弊捷径 |
|---|---|---|---|
| **CUDA kernel 优化**（KernelBench / B200） | 平均 SOL（0.5 = PyTorch eager，1.0 = 硬件极限） | torch.compile（SOL ≈ 0.547） | 硬编码已知输入分布的统计量假装更快 → 评测输入每次随机仿射 |
| **训练脚本提速**（nanoGPT speedrun / 8×H100） | 达到 val_loss ≤ 3.28 的**认证墙钟训练时间** | Recursive 185.4 / 80.6 / 77.3 s | 偷换 attention kernel、环境漂移 → 强制环境对齐、用真实 FA3 |
| **训练效果优化**（nanochat / B200） | 固定预算下的 **val_bpb** | Recursive 1.0587 / 0.9344 / 0.9109 | SDPA fallback、假 attention shim → 必须用真实 FA-4、逐字节对齐环境 |
| **量化因子挖掘**（因子挖掘 / 筛选 / 组合） | 样本外因子表现 / 组合收益 | 领域强基线 | 前视、数据泄漏、过拟合 → 样本外评估、可复现审计 |
| **自动写论文**（EMNLP/ACL/AAAI） | 通过完整同行评审标准 | 真实强基线复现 | pilot / 合成 / 同源对比冒充完整证据 → 全规模证据门、结论溯源 |

看出共同点了吗？**每一行都是「拿一个诚实的硬指标，在不作弊的前提下，连续数天逼近极限 / 打败强基线」。**
这正是第 2 节那套「不空转 / 不打滑 / 不卡死」和第 7 节那套防造假护栏共同服务的目标——它们对 kernel、
对训练、对因子、对论文是**同一套机制**，只是把关的指标不同。

> 以「自动写论文」为例（它的任务链最长、最能压测整套机制），Argus 把它拆成 8 个阶段，engineer 产出、
> reviewer 逐阶段裁决：
>
> ```
> research → plan → benchmark → run → analysis → draft → review → submission
> ```
>
> 内置 **64 个 skill**（54 engineer + 10 reviewer）作为 agent 的复用手册，缺能力时在线蒸馏；目标会议
> EMNLP/ACL 或 AAAI，格式自动切换。其它问题（kernel / 训练 / 因子）任务链更短，但走的是**同一套
> 「规划 → 执行 → 审稿 → 记忆审计」引擎**。

## 6. 自进化：把需要专业知识的 OOD 问题，变成「会做」

第 5 节那张表藏着一个尖锐的问题：**一个引擎，凭什么能同时啃 B200 上的 CUDA kernel、一个特定训练栈的
提速、一套特定市场的因子？** 这些都是 **OOD（超出基座模型训练分布）、需要专业领域知识**才能解的问题——
基座模型并不「天生就会」某个具体架构的 kernel 对齐陷阱、某个训练栈的真实 FA-4 接法、某个市场的因子构造。

Argus 的答案不是「换个更大的基座模型」，而是**自进化**：把不会的，通过「执行 → 学习 → 沉淀」变成会的，
并且沉淀成**可复用、越用越准**的能力。

**机制（都在代码里，不是 PPT）：**

- **缺能力就当场长一个（miss → 蒸馏）。** 遇到没有现成 skill 的任务，scientist 在线生成一个新 skill——
  它的作者 prompt **明确要求去看「有经验的从业者是怎么解这类问题的」**（codex 原生联网搜索），再和本机
  实测结合，写成一份给「能干的同行」看的实操手册，而不是空泛原理。**这就是把专业 know-how 从「网上 +
  真机」抓进系统的入口。**
- **每个任务结束都更新能力（lifecycle 决策表）。** 任务一结束，系统按 (结果, 是否成功, 有没有命中 skill)
  自动决策：成功 → **强化**（把这次轨迹回写进 skill）；没命中 → **蒸馏**一个新 skill；非致命失败但有教训 →
  **修订**（把教训提升进 skill）；连续 3 次惨败 → **退役**（归档）。**能力库因此每个任务都在自我校准**——
  不是静态文档，是会长记性的器官。
- **失败也沉淀。** 一个被否决的方向，留下的不只是「此路不通」，而是可复用的 skill、benchmark 代码、审计
  产物——喂给下一次尝试。

**为什么这对 OOD 问题特别关键：** 一个只靠基座模型「一次性聪明」的 agent，在专业问题上很快撞天花板——
它不知道某个架构的隐藏带宽、某个 kernel 的对齐陷阱、某个市场的微观结构。Argus 不假设自己一开始就会：
它**搜怎么做、上真机试、把真正奏效的写回去**，于是第 N 次碰同类问题时，手里已经攥着前 N−1 次攒下的专业
手册。**「越跑越会」不是修辞——它是 reinforce / distill / revise / retire 这张决策表每个任务都在执行的结果。**
所以把 Argus 指向一个它一开始「不会」的专业 OOD 问题是合理的：**它会把「不会」当成第一个要解决的子问题。**

> 注意这仍然严守第 3 节的哲学：**进化的内容**（什么 know-how 值得记、哪条教训该提升、这个 skill 是不是
> 该退役）**是 agent 的判断**；harness 只提供「miss 了就触发蒸馏、任务结束就跑决策表」这种领域无关的机械
> 触发，从不替 agent 决定一个 kernel trick 对不对。

---

## 7. 诚信底线：为什么它的结果可信

自主跑研究最大的风险是**作弊**——agent 可能学会「把数刷好看」而不是「把事做对」。这是唯一允许
harness 立「硬规则」的地方，因为它管的是诚信，不是研究选择：

- **只用真实指标 + 真实测量**，不把 pilot / 合成 / 同源对比当完整结果；**严格环境对齐**——指标
  （kernel 的 SOL、训练的 val_bpb / 墙钟时间）只有在和参考数**完全相同的环境**里测才算数，禁止偷换
  kernel、SDPA fallback、版本漂移；
- **主动堵 reward hacking**（如评测输入每次随机仿射，让被测代码无法硬编码已知输入的统计量假装很快）；
- **公平对比**：基线在同硬件、同脚手架上复现，讲清 caveat，like-for-like；
- **留可复现审计链**：idea / benchmark / 原始跑 / 结论→证据 / 审查记录全程可逐项检查；
- **绝不报喜报早**：跑出多少报多少，失败/被污染/做不到都直说，不把抖动或作弊刷出来的数当真结果。

---

## 8. 为什么值得关注

- **它解决的是「自主 agent 怎么不退化地长跑」这个真问题**，不是又一个能跑 demo 的壳。第 2 节那套
  不空转/打滑/卡死的工程，是把「跑 5 分钟很惊艳」变成「跑 5 天还在有效产出」的关键，且**领域无关**——
  kernel / 训练 / 因子 / 论文都只是它当前的载体。
- **它让失败变得有用**：一个被否决的方向，会留下可复用的 skill、benchmark 代码、审计产物，喂给下一次。
  每失败一次，能力库和把关标准都更强一点。
- **它是一个会自我增强的平台押注**，不是一次性 demo——价值在「这套能可信、可复现、不停机、越跑越强的
  自主研究机器」本身。

## 9. 怎么把它跑起来

```bash
# 1) 一次性向导：配作者身份、三个 agent 的 API、GPU 分配、防回收 keep-alive
argus-skill --setup

# 2) 在目标项目目录中启动 Argus；项目结构由 Agent 根据任务自行创建
mkdir -p ~/research/world-model && cd ~/research/world-model
argus-skill

# 3) 在 cockpit 中提交目标，然后查看运行状态（断 SSH 不影响后台运行）
argus-skill --status     # 当前状态
argus-skill --watch      # 实时驾驶舱
argus-skill --follow     # 事件流
```

> 起守护进程前有**硬门禁**：必须同时给齐研究目标 + 至少一条机器规则，缺则直接退出并打印指引——
> agent 必须被**显式**告知目标和规则，而不是让程序去猜（第 3 节理念的落地）。

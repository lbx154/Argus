# 角色交接：从原则到设计

英文版：[role-handoff-design.md](role-handoff-design.md)

状态：提案（2026-10-16）。实施进度见[路线图](ROADMAP.zh-CN.md)；本文解释每一项为什么存在。活性部分（[接力棒](#接力棒)）从修复[不会结束的交接](#不会结束的交接)中列出的缺陷开始，每个修复都是某一条不变量的一个实例。

## 为什么写这份文档

Engineer、Reviewer、Planner 和 Manager 之间的交接，是 Argus 中被修得最频繁的地方。仓库历史里有 774 个提交提到 Reviewer，182 个提到交接；2026-10-08 到 2026-10-10 之间，同一类缺陷落地了大约二十个修复。2026-10-16 的审计又发现了十来个，在 `ef216a16` 中修复，而每个修复依然只补了一个实例。

这些缺陷并不相互独立。每一个都是一种偏离了 Argus 已在 [PRINCIPLES.zh-CN.md](PRINCIPLES.zh-CN.md) 中写明的原则的交接实现。原则文档也说明了这时该怎么做：改实现，而不是加例外。本提案就是这样做的。

## 交接的第一性原理

Argus 使用多个角色只有两个理由：生产者无法给自己的独立判断，以及生产者不具备的权限。分工或节省上下文都不需要第二个角色。

因此交接只为一个目的存在：**让判断方在不被生产方引导的情况下，判断世界是否达到了约定的状态。** 由此推出四条性质，每一条现在都已写进原则：

| 性质 | 原则 | 缺少它会怎样 |
| --- | --- | --- |
| 判断方阅读变化本身，变化由 Runtime 界定，而不是生产方的叙述 | 1、5 | Reviewer 评判的是一个故事；故事漏掉的工作被一并接受 |
| 每条记录只有一个作者；Runtime 的介入是 Runtime 自己的记录 | 1 | 没人分得清 Reviewer 到底说了什么；守卫把宿主占位记录当成判决来计数 |
| 标准由其主人在候选出现之前确定 | 5 | 审阅中途改标准；正确性问题和范围问题无法区分 |
| 访问问题和障碍交给能处理它的一方 | 8 | Reviewer 读不到或跑不了某样东西，就把工作退回给同样无法修复它的 Engineer |

这些性质让判断可信，但不能保证判断会发生。交接还必须**结束**。一个没有人有义务结束的等待、一次把原样工作退回给同一方的退回、一个没有任何人有权做出的决定，都会像崩溃一样让 Programme 停下来，而在长程任务中这是更常见的失败。四条不变量保证每次交接都会结束，见[接力棒](#接力棒)。

## 当前实现的做法

基于 `origin/dev` 的 `a05dcb98`，以及上一个生产实例和当前试用实例的运行记录。

### Reviewer 评判的是叙述，而且只看最后一轮

- `roles/prompts/reviewer.py`（`_changed_artifact_block`）最多列出二十个 mtime 晚于当前审阅窗口起点的文件名，没有内容 diff。`.argus` 被整个跳过，所以 `.argus/runs` 下的运行产出从不出现。
- 同一个提示词写着“Engineer 自己的叙述是主要依据”；执行日志只作为一行兜底。
- 每次审阅完成后窗口就关闭，所以 `done` 评判的是自上次审阅以来的变化，而不是整个任务。更早的轮次只以转述的散文形式到达 Reviewer。
- 在 `ef216a16` 之前，Copilot Reviewer 读不到提示词里点名的文件：14 次线上 Reviewer 调用中有 11 次读取被拒。
- `skills/round_checkpoint.py` 会给 git 工作目录打快照，但它唯一的触发条件（`checkpoint_recommended`）从未被原生审阅路径设置，也没有任何代码读回这些 ref，而且检查过的 22 个真实工作目录，根目录没有一个是 git 仓库。

### 判决被改写，来源靠猜

- `ReviewDecision.review_source` 默认为 `"reviewer"`，有十二个调用点在它为空时回落到 `"reviewer"`。来源信息分散在五个字段里（`review_source`、`reviewer_authored`、`reviewer_words`、`host_notes`、`host_placeholder`）。
- 有四条宿主路径会就地修改 Reviewer 写下的判决：venue 验收（`core/venue_review.py`）、后台运行保持（`engineer/runner.py`）、操作员提问政策，以及终态问题剥离（`engineer/round_settlement.py`）。被 venue 改写过的判决封存时仍然标记 `producer_role=reviewer`。
- 下一轮 Engineer 提示词据以构建的 `RoundLoopState.reviewer_next_action` 有五个写入方。
- `events.jsonl` 是唯一的只追加记录。`latest.json`、任务简报和 Backlog 结果字段都是投影，但其中好几个是直接写入的，而不是推导出来的。

### 宿主在做语义判断

| 宿主规则 | 位置 | 它做出的判断 |
| --- | --- | --- |
| Engineer 消息非空即为“成功的工作信号” | `round_stop_signals._runner_result_has_successful_work_signal` | 是否发生了工作 |
| 两个障碍在词重叠达到 60% 时视为同一个 | `obstacle_stall.SAME_OBSTACLE_OVERLAP` | Agent 是否卡住 |
| 超过软上限后，连续两次判断没有 `forward_progress=true` 就判定任务停滞 | `round_settlement` | 工作是否在推进 |
| 从硬上限起，没有明确进展的 `continue` 变成 `blocked`，而 Reviewer 从未被告知这条规则 | `round_settlement` | 同上 |
| Engineer 最多连续两次自我交接（`ef216a16` 中加入） | `round_self_review` | 工作何时需要审阅 |
| 拒绝适配器在下一步动作前插入一段 playbook | `round_settlement` | Engineer 应该做什么 |

轮次循环和 Reviewer 的 10,400 行代码中，大约有 2,000 到 2,500 行用来维护这些规则、占位记录、改写及其来源渲染。

### 审阅的精力实际花在哪里

上一个生产实例和当前试用实例中的 59 次 `continue` 判决，按其陈述的理由分类：

| 理由 | 次数 |
| --- | ---: |
| 在等一个正在运行的作业，没有新东西可判 | 30 |
| Reviewer 缺少任务所需的访问权限或工具 | 17 |
| 正确性或执行缺陷 | 5 |
| 验收检查之外的顾虑 | 4 |
| 某条验收标准未满足 | 3 |

大多数没有接受工作的审阅调用，要么没有新东西可判，要么根本无法判断。除此之外，试用实例收敛得不错：25 个被审阅的任务中有 22 个以 `done` 结束，其中 13 个一轮完成。

### 标准来自多处

Planner “在有用时”写 `acceptance_check`；39 个有记录的任务中有 35 个写了。Engineer 在任务契约中看到它，Reviewer 则看到它被拼接进 `review_objective`，旁边还有原始请求、目标契约条款和阶段指引。判决是自由散文：没有任何东西把 `approve_review` 和这些标准绑定起来。把完成与明确的目标状态绑定的修复（`fix/completion-objective-status`）从未合入 `dev`。

### 不会结束的交接

通过阅读 `origin/dev` 在 `8c188e69` 的代码测得；下面每一项都追到了具体代码行。

去重后大约有三十种不同的交接。按工作接下来去向哪里，它们可以归为六种动作：

| 动作 | 方向 | 现状 |
| --- | --- | --- |
| 委派 | 向下：产生新工作 | Manager 派发；Planner 入队与认领；启动 teammate 和 subagent；咨询 advisor |
| 送审 / 退回 | 平级：交给独立判断方，或退回生产方 | Engineer 交给 Reviewer；Reviewer `continue` |
| 上报 | 向上：交给握有权限或能排除障碍的一方 | 向操作员提问；`replan_requested`；`blocked`；“Planner 需要方向” |
| 挂起 | 向外：交给外部世界或时间 | 等待后台运行；Planner `WAKE_ON`；十一种 `paused_*` 状态；Manager WAIT |
| 续接 | 同一角色，稍后继续 | Engineer 自我交接；角色会话轮换；暂停后恢复；daemon 蓝绿切换 |
| 插话 | 向内：自上而下打断正在工作的持有者 | 操作员 STEER；Manager steer 与 wait；暂停与中止 |

Reviewer 的判决不是第七种动作：`continue` 是退回，`replan_requested` 和 `blocked` 是上报，`done` 是接受。第七种只以隐式形式存在，即宿主改写模型做出的动作：判决改写、问题被改成 replan、`PLAN_RETRY` 丢弃整批 Planner 任务、Planner 的阶段推进绕过 Manager 直接生效。

这三十种交接各自带着自己的等待、超时和计数器，十几个阈值（2、3、4、12、24、60、120、300 秒、1,800 秒、3,600 秒、0.6 词重叠）各自修补一个循环。由于没有一条统一规则规定交接如何结束，出现了四类缺陷：

| 类别 | 发生了什么 | 例子 |
| --- | --- | --- |
| 孤儿等待 | 持有者在等一个没有任何人有义务产生的事件，且没有期限 | 依赖 `research_incomplete` 或 `infra_blocked` 工作项的任务永远 pending：级联只在终态时触发，而 Planner 只能退役 pending 项。runtime 故障熔断只有在一个 `runtime_failure_canary` 任务通过后才会复位，而没有任何代码创建这种任务。进程还活着但已卡死的 subagent 永远被视为健康，因为 `stale_after` 算出来了却从未被比较。蓝绿切换的候选进程 60 秒内拿不到锁就退出，而此时切换请求已被消费，项目没有了 daemon。不带任务的 Manager WAIT 会冻结全部规划。 |
| 无界往返 | 工作来回传递，却没有机械的变化度量 | `require_independent_review=False` 的任务不经结算就自我继续，而 `max_rounds` 默认为 0。`forward_progress=true` 让停滞守卫失效，轮次计数每次恢复都从头开始。team 任务重试没有预算。 |
| 权限真空 | 某个决定没有有权做出它的一方 | 操作员在场但禁止提问时，没有任何人可以接受残余风险。Manager 的监督通道停不掉一个任务。 |
| 交接失真 | 动作在转换中丢失或被送错 | 同时声明等待并提出任务的 Planner 判决会丢掉这些任务。在已归档工作项上提出的问题被吞掉。daemon 不把 `early_stopped` 和 `crashed` 视为终态。一张过期的决策卡片会回答一个更新的问题。 |

## 目标设计

### 记录

- **事实**：事件日志，以及宿主拥有的工作区快照。
- **作者记录**：每个参与方只追加自己类型的记录。Reviewer 的判决只来自它的审阅动作。宿主的介入，例如后台保持、提问政策、venue 最低分、预算停止或未被判断的回合，是引用其所影响判决的 `host` 记录。两类记录写入后都不再修改。
- **有效结果**：由结算根据判决和介入计算得出。它是派生值，与派生它的输入一起记录。
- **投影**：`latest.json`、任务简报和 Backlog 结果字段都由记录重建。`CHECKPOINT.md` 仍是 Engineer 自己的工作笔记，不是验收证据。

没有已知作者的记录是缺陷，而不是 Reviewer 的判决。

### 候选与基线

- 宿主为每个项目维护一个私有快照库：项目状态目录下的一个裸仓库，其工作树就是任务工作目录。用户的工作目录、分支和 index 从不被触碰。
- 生成的产出、虚拟环境、嵌套仓库和超过大小上限的文件只记录在清单中（路径、大小、mtime），不存内容。在最大的线上工作区（220 GB，16.4 万个文件）上，这样只剩 2,141 个文件：首次快照 3.7 秒，之后每次 0.03 秒。
- 快照以 `(mission, run, sequence)` 标识，这个标识记录在事件日志中，并用作私有 ref 的名字。Git 的对象 id 只是内部细节，因此不会引入新的哈希标识。
- 基线是任务开始时的快照，只有在 Reviewer 接受一个候选时才前移。
- 候选是请求审阅时拍下的快照。Reviewer 收到的是从基线到候选的变化：文件名与状态、有界的文本 diff、清单变化、Engineer 执行过的命令，以及任何新的外部结果。Engineer 的叙述放在变化之后，并标注为生产方的叙述。
- 判决注明它评判的是哪个候选。阶段证书或回放的验收只对那个候选有效。

### 何时审阅

- 在 Engineer 宣布候选，或达到委托人设定的检查点预算时请求审阅，而不是每个 Engineer 回合之后都请求。
- 如果候选与上一次被评判的候选相同，且此后没有新的外部结果或操作员指令到达，宿主记录这一事实，不调用 Reviewer。单这一条就消除了最大的一类 `continue` 判决。
- 后台工作在结果出现时才评判。Engineer 在自己的回合里等它，没有人让 Reviewer 去判断“什么都没发生”。

### Reviewer 的决定

- 验收标准通过引用来自任务契约，由写下它的一方拥有（Planner、Manager 或操作员，见 [goal-contract-authority.md](goal-contract-authority.md)）。
- 交给 `→ done` 或 `→ engineer` 的审阅对每条标准给出状态。只有每条标准都满足，或被其主人明确接受，才能批准。
- 标准之外的顾虑是后续事项：记录下来，转给 Planner 或 Manager，不阻塞。违反真实性底线（虚假声明、伪造证据、来源断裂）始终阻塞。
- 拒绝要说明什么能改变判决。
- Engineer 无法排除的障碍，例如缺少访问权限、缺少工具或契约冲突，上报给宿主或契约主人，而不是退回给 Engineer。

### 能力与职责匹配

一个角色要么得到其决定所需的能力，要么这个决定交给别人。Reviewer 拥有和 Engineer 一样的权限，所以关键检查由它自己重跑；它有没有动工作区，由宿主比较前后两张工作区快照来确认，靠的是事实而不是权限。

### 宿主执行预算，不判断进展

每个任务的轮次、墙钟时间和成本是由 Manager 或操作员设定的预算。到达预算时，宿主停止并记录这一事实，由 Manager 决定接下来怎么办。宿主不根据消息长度、词重叠或缺失字段估计进展，Reviewer 的提示词也不解释它无法影响的宿主机制。

### 接力棒

每一项未结束的工作（一个任务，或者没有可运行任务时项目的规划位）在任何时刻都恰好有一个**持有者**：Engineer、Reviewer、Planner、Manager 或操作员。一次交接就是一段自然语言说明，加上一行写明下一个持有者：

```text
<做了什么、发现了什么、还剩什么、为什么交给下一位>
→ reviewer
```

这一行只有六种取值：`engineer`、`reviewer`、`planner`、`manager`、`operator: <一句话问题>`、`done`。路由是自由的：任何持有者都可以交给任何角色，比如 Reviewer 发现验收标准冲突时直接交给 Manager，Engineer 发现任务划分有误时直接交给 Planner。宿主从不决定工作去哪里，它只执行四条不变量，这四条合起来就是整个状态机：

1. **单一持有。** 一项工作同一时刻只有一个持有者；工作之间只通过依赖图相互等待，而依赖图无环，因此不会形成循环等待。一个问题只挂起它所在的工作项及其下游，绝不挂起整个项目，也绝不挡住操作员的控制通道。
2. **等待在持棒者自己的回合里，由后端处理。** Argus 没有“等待”状态，也不替任何持有者盯着什么（原则 1：Runtime 不当家长；自检问题 7：后端自己能做，就别替它做）。长任务分离启动，在同一回合里用后端的阻塞命令等它结束。问题交给操作员；操作员无法被询问时交给 Manager。没有任务在跑时，守护进程每过一次空闲退避就再问一次 Planner，不管它上次答了什么；不拿以前的回答顶替这次。后台调用预算（`argus/core/call_guard.py`）用完后，调用在发出前被拒、不花钱，也不算 Planner 失败，直到下一次进展。
3. **原样退回即上交。** 如果工作要回到一个已经持有过它的持有者手里，而候选没有变化，此后也没有新的外部结果或新的操作员输入，那么宿主不再调用这个模型，而是把工作沿权限梯 Engineer → Reviewer → Planner → Manager → 操作员 上交一级。“有没有变化”是从候选快照和事件日志读出的机械事实。它按任务谱系计数，所以恢复、replan 或换一种说法都不会让它清零。对 Engineer 来说，交到它手里、它还没据此干过活的那份审阅意见算新输入；它再原样交回时，仍会在 Reviewer 那一级被拦住。Reviewer 上次判的是 `→ done` 时不往上交：那次通过直接沿用，不调用模型，记录里写明沿用的是哪次判决。宿主拒收了那次通过（它结束的任务失败了，或被送回重跑），这本身就是新的外部结果：那次通过不再沿用，没有变化的候选越过 Reviewer 往上交。

   每一级只决定它自己的事。Planner 这一级管的是工作内容：路线被否、没有可行的想法，就重新规划；没有符合操作员意图的路线了，就带着试过什么和选项去问操作员。Manager 这一级管的是**流程**：同一个错误反复出现，环境、工具、凭据或额度出故障，某个角色原样交回，交接来回打转，超时，阶段因为机械原因推不动。它拿到一份“流程卡住”简报（什么在重复、报了什么错、最近改了什么），在自己的权限内排查，然后给出诊断和一个去向：修好了，交回持棒者重试；交给 Planner，按诊断重新规划；或者只问操作员必须由他定的事。诊断写在这项工作自己的记录上。它不决定操作员想要什么，不写计划，不验收候选，也不宣布阶段或项目完成（`argus/manager/process_debug.py`）。
4. **权限无真空。** 每类决定都有主人。主人无法被询问时，决定顺延给下一个被允许的一级，而不是消失。只有不可逆的决定可以没有期限地等待操作员，而且只在操作员能被询问时才可以。可逆的问题要附带提问方的默认做法（“T 时间内没有回答，就按 X 继续”）。

| 决定 | 主人 | 主人决定不了时 |
| --- | --- | --- |
| 操作员想要什么：目标、他的话按哪种理解、他的必经步骤、他接受的风险 | 操作员（Manager 只问和转达，从不替他决定） | 只有操作员说了“别问我”时由 Manager 决定，记在它自己名下并列入报告 |
| 接受一个候选 | Reviewer（不要求审阅时为 Engineer） | — |
| 创建、拆分、排序、退役或替换工作 | Planner | 操作员，通过一个带选项的问题 |
| 变更阶段 | 完成闸门，看证据（审过的成果、领域的阶段完成检查、必经步骤）；Planner 提议“阶段就绪” | 证据和操作员说过的意图冲突时，问操作员 |
| 项目完成 | 同一个完成闸门 | — |
| 停止一个任务 | 操作员，或按操作员指示的 Manager | — |
| 支付、对外发布、破坏性操作、发布版本、凭据 | 操作员 | 只在“别问我”时由 Manager 决定，并记录 |

每个决定一个主人（2026-10-26）：角色不合并，去掉重叠的权限。Manager 面向操作员，并在流程卡住时排查；Planner 做计划，Reviewer 的质疑直接作为它的输入，中间没有 Manager 裁决；一个完成闸门（`argus/manager/stage_decider.py`，由 `Manager.decide_stage_transition` 执行）推进阶段、判定项目完成，不调用模型，Manager 用一小段话告诉操作员发生了什么。Planner 提议阶段就绪的方式：规划收尾这个阶段的任务，或者它规划的工作已全部通过验收，或者用 `advance_to_stage`；提议项目完成用 `→ done`。不再有 Manager 的阶段决定回合。

“无法被询问”指操作员说了“别问我”，或者这次运行没有操作员（原则 8）。这时操作员的权限交给 Manager。Manager 替操作员作出的每个决定都记在它自己名下，附上引用的证据，并列入交付报告。

**为什么每项工作都会结束。** 每次交接只会是三种情况之一：

- 改变了候选或带来了新事实，这会消耗预算。
- 上交一级，最多发生四次。
- 结束这项工作。

一次等待最多持续它所在的那个回合。因此在有限次交接之内，每项工作要么完成，要么被放弃，要么停在一个能被询问的操作员手里等一个不可逆的决定，而这不会阻塞任何其他工作。死锁不可能发生，没有变化的模型调用次数以权限梯的高度为上界。

**它替代了什么。** 已完成（2026 年 10 月）：接力棒下面不再有轮次状态，旁边也不再有具名的暂停状态。

- `continue` 就是 `→ engineer`，`replan_requested` 就是 `→ planner`，`blocked` 就是 `→` 能排除障碍的一方，`done` 就是接受一个具名候选。一轮、它的记录和它结算的任务直接写持有者（`engineer`、`planner`、`manager`、`operator`、`done`），不再翻译回旧状态。旧版本写下的记录只在一处读：`holder_of`（argus/core/handoff.py）和 `settledStatus`（frontend/core/src/missionOutcome.ts），从不再写。`blocked` 只留在宿主停下一轮、什么都没判断时写的记录上（暂停、服务中断、审阅者没回话）：它不指名持有者，所以不会告诉人"经理在定"。
- 交给 Manager 或操作员的任务挂起在他们手里，不管是谁交的，都不记为失败：Manager 交给操作员的问题挂起的就是这个任务，回答后恢复的也是它，不另开副本。
- `paused_*` 状态是一种挂起，原因只是数据（argus/core/stop_kinds.py），待办行、Planner 结论和给操作员的提示都一样；措辞由原因决定。旧的行和事件经同一张表读入。
- Planner 没有新工作可开时，写明下一个持有者：`→ engineer`（在跑的工作决定下一步）、`→ manager`（流程因机械原因卡住）或 `→ operator: <问题>`。不再有等待契约。
- 没有 Manager 的阶段决定回合，也没有“Team report”回合：阶段经完成闸门推进，阶段问题从不等 Manager 会话。
- 没有计划质疑裁决：Reviewer 的 `→ planner` 原样交给 Planner。
- Planner 规划期间操作员发来的话不会被跳过：提交计划时，这一轮规划开始之后记进对话记录的操作员消息会变成一条只给 Planner、只用一次的指示，这一版计划不开工，Planner 带着它重新规划。
- Engineer 的七个 footer 键和等待行变成上面那一行；等待本身移进 Engineer 的回合。

只有副作用需要时才保留结构化载荷：Planner 任务的标题和目标（有依赖和所属路径时再加上它们）、一个问题、一次授权。这一行按宽松方式解析：大小写、操作员语言里的角色名、Markdown 修饰都不影响。缺失或无法解析的一行绝不会结束任务，也绝不意味着 `done`：候选有变化就交给 Reviewer，没有变化就上交一级。

### 监督者

接力棒在四个角色、操作员和外部世界之间传递，监督者从不持棒。它就是以前坐在屏幕前看着的那个人，只看整体流程是否顺畅：谁拿着棒、交给了谁，每个回合用了多久、花了多少钱，有没有同一个角色反复被叫却拿不出新东西，有没有等了很久没人动，方向是否越走越偏。活干得对不对仍归 Reviewer 判断。它不做任何决定：停任务、纠偏仍归 Manager 或操作员。

Engineer、Reviewer、Planner 每结束一个回合它看一眼，自己的回合不算，只读这个任务的事件。同一个任务里它续用一个会话，只读上次看过之后新增的事件；任务结束，会话随之结束；规划不属于任何任务，每次重新看。没人真正上场的回合不算回合，比如连续失败后被暂缓的 Planner 调用。流程不顺时写一行 `→ manager: <一句话和证据位置>`，记为一条带任务标识的 `life.observer.note` 事件：Manager 经督导通道听到，和"一轮卡住"一样算一次只报一遍的新情况，由 Manager 决定继续、纠偏、暂停还是停；没有 Manager，就提醒操作员。插话不移动接力棒，也不算作候选有变化；同一句话不说第二遍。

## 删除什么

替代机制就位后删除，每一项对应一个独立的路线图工作项：

- `_changed_artifact_block` 和 mtime 审阅窗口，由候选 diff 替代；
- `skills/round_checkpoint.py` 和 `ARGUS_SKILL_ROUND_CHECKPOINT`；
- `venue_review`、后台保持和提问政策中的就地判决改写，由宿主记录替代；
- `review_source` 的 `"reviewer"` 默认值和回落，以及相互重叠的来源字段；
- 非空消息即进展的判断、障碍词重叠、软硬进展规则、自我交接上限和拒绝适配器 playbook；
- Reviewer 提示词中解释 harness 机制的段落；
- `review_objective` 拼接，由通过引用读取任务契约替代；
- `reviewer/_parsing.py` 中没有生产调用方的散文解析路径；
- 其余用来代替“原样退回即上交”的循环计数器：空回合与停滞连击、Planner 的探针任务及其固定的重新授权节奏；
- 作为独立状态的十一种 `paused_*`，由一种挂起记录替代；
- Planner 的等待契约字段和 Engineer 的 footer 键，由那一行交接替代。

## 兼容性

- 现有状态保持可读。新的记录类型和快照 id 只做增量添加，旧的轮次文件、事件和 Backlog 字段不被改写。
- 变更前启动的任务按其启动时的规则完成。没有迁移会改写进行中的状态。
- 每个路线图工作项都是独立、可审阅的变更。按照 [runtime-maintainability.md](runtime-maintainability.md)，API、存储格式、阶段语义和部署不在同一个补丁里变更。
- 旧 footer 不再读取：Engineer 和 Reviewer 的提示词都要求写交接行，旧消息里残留的页脚行只当作正文。

## 如何衡量成功

按照原则 9，成功在真实任务上与匹配对照比较来衡量，而不是数 Gate。对每个被接受的任务，跟踪：

- Reviewer 调用次数，以及其中在未变化候选上的占比（目标：零）；
- `continue` 判决的理由分类，同上；
- 被接受后又被发现不完整的任务（误判 `done`）；
- 墙钟时间、token、模型调用次数和成本；
- 操作员问题和上报，以及由谁解决；
- 没有任何持有者能够处理的工作项，以及它们停留了多久（目标：没有）；
- 任何角色在未变化候选上发起的模型调用（目标：零）；
- 每一级的上交次数，以及每个到达操作员的工作项最终如何解决。

路线图中的指标工作项从 `events.jsonl` 生成这些数字，后续每一项都可以对照同一个基线报告效果。

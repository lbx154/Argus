# Argus 路线图：从 0.1.8 到正式版 1.0

英文版：[ROADMAP.md](ROADMAP.md)

## 一句话

**交给 Argus 一个真实的科研或工程目标，它能自己做完；它说"完成"，就是真的完成了；花了多少钱、多少时间说得清楚；
过程随时看得见；越用越好。** 做到这些，就是 1.0。

本文只讲 `dev` 分支上的计划和状态，不代表已经发布。里程碑按先后排，不承诺日期。每个任务只有一行状态；
怎么走到这一步的，看对应的提交和 PR，这里不再写。旧编号（HO-1、CO-2……）保留在"吸收"一栏，
以前的链接和分支名照样能找到归属。

## 我们现在在哪

在 `chore/merge-1023`（`190d9b7f`，2026-10-22）上实测：

- **规模**：`argus/` 里 19.8 万行 Python，`tests/` 里 20.2 万行；TypeScript 7.5 万行；766 个测试文件；3,039 次提交。
- **错误还是容易被吞掉**：`argus/` 里有 2,679 个 `try:`、694 个 `except Exception`；类型检查存量 1,433 条（2026-09-12）；
  每次提交只在 Linux 上跑后端测试。
- **角色靠写一段文字交接，宿主再去拆**：大约 3,400 行代码专门把自由文本拆成决定。五轮自测（286 次模型调用）里，
  问题丢了选项，内部文件名漏到用户眼前，Manager 三次自己拍板了有歧义的需求，也没记下这是替用户做的假设。
- **没有尺子**：合并前不回放真实运行；没有标准任务集，没有注入缺陷的评测集，也没有和直接用 Agent 的对比。
  简单任务 Argus 要 53 秒，直接用 Copilot 是 28 秒。
- **"越用越好"还没有证据**：两次真实测量都没看到任务质量变好。
- **上手难，多人用也难**：得先装好并登录一个编程 Agent 命令行；Mac 安装包没签名；自托管网页版没有账号。

## 为什么按根源来排

旧版列了 134 条，都是症状。实测的约 40 个问题能归到四个根源上，治好一个根源，一串症状一起消失：

1. **角色靠写一段文字交接，宿主再拆。** 问题丢选项，内部字段漏到界面，同一段话既当路由数据又当给用户的话。
2. **同一件事存好几份**，各处自己推算：摘要文件、任务简报、待办里的结果字段各写各的；前端把后端已有的状态再算一遍。
3. **宿主替角色猜下一步**：文字读不出就套默认去向，重试时再问一遍模型，用守卫和计时器判断"卡住了"。
4. **规则散在多处、互相打架**："什么时候问用户"在各份提示词里有七个版本。

这四条下面还压着两件事。没有**尺子**（回放测试和标准任务集），哪个修复都证明不了有用，八条标准里有四条根本没法判断。
**代码量**本身也是根源：每多一份拷贝、多一条补救分支，就多一个藏问题的地方。

所以核心是六条主线：四个根源各一条，加上尺子和做减法；第七条主线在这之上把内核迁到 TypeScript。
产品线的目标不变，各自写明依赖哪条主线。

### L7 TypeScript 内核（只要 Node）

目标是只有 Node 的机器上一条命令装好 Argus：Argus 驱动的后端都是 npm 包，用户本来就有 Node，去掉的是第二个运行时
Python。内核很薄：按表单的 `to` 在角色之间交接，记录发生了什么，守住权限边界。阶段机、观察员、经理监督，以及看门狗、
重试、猜测这几层不移植，直接不做。新项目在内核自己的状态根目录（`~/.argus`）里跑；Python 运行时把手上的项目跑完后删除。
依赖科学计算 Python 栈的领域插件，通过插件 worker 接进来。设计和进度见 [typescript-core.md](typescript-core.md)。

## 如何参与

1. **按新编号挑任务。** 适合新人的：L1.4 的反向指标、L3.3、L5.3、L6.2、L6.4（一次一个文件）、P1.4、P1.8、
   P3.4（一次一个领域）。
2. **先说一声**：在 issue 或草稿 PR 里写上任务编号。从 `dev` 拉分支，命名 `fix/<编号>-<简称>` 或 `feat/<编号>-<简称>`；
   见 [CONTRIBUTING.md](../CONTRIBUTING.md)。
3. **写明治哪个根源。** 说清这次改动服务哪条主线或根源，对应[原则](PRINCIPLES.zh-CN.md)里的哪一条。
   说不出来的新机制不进核心。
4. **挪代码就要删代码。** 挪代码的 PR 也要删掉一些；L6 的几个护栏不许上涨。
5. **先写失败的测试**；跑回放测试和全部 Python 测试。旧数据必须还能读。
6. **发布清单。** 只改 Python 时清单会过期，要等 `python -m argus.release_tools.build_release` 跑过；
   在 PR 里说明跑没跑。改了前端源码，就把重新构建的界面一起提交。
7. **一个 PR 只做一件事。** 别在同一个补丁里同时改接口、存储格式、阶段语义和部署。
8. **做完更新状态行**：一行，加上提交或 PR 链接。来龙去脉写在提交说明里。

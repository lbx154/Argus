# Argus 路线图：从 0.1.8 到正式版 1.0

英文版：[ROADMAP.md](ROADMAP.md)

## 一句话

**把一个真实的研究或工程目标交给 Argus，它能自己把事情做完，说"做完了"的时候是真的做完了，
花了多少钱和时间说得清，过程随时看得见，而且越用越好。** 做到这一点，就是正式版。

这份路线图列出了从今天（0.1.8）走到那里要做的全部工作。每一项都写明现在的问题、要做什么、
做完是什么样子，可以直接认领。全部做完，下面八条正式版标准就全部达成。

本文只描述 `dev` 分支的计划和状态，不代表任何版本已经发布或部署。里程碑按先后排列，不承诺日期，
同一里程碑内的任务大多可以并行。

## 正式版的标准

1.0 不是一个日期，而是下面八件事同时成立。标有"初定"的数字，要等相应的指标工具先把今天的基线
测出来（多数在 0.2 完成），再在本文中校准。

| # | 标准 | 用什么衡量 | 1.0 的目标 | 主要靠哪些任务 |
| --- | --- | --- | --- | --- |
| 1 | **靠得住**：没人盯着也能跑完；崩溃、重启、断网之后不丢、不重；出了错能看见 | 标准任务集中长任务的无人值守完成率；故障注入测试；关键路径上"把错误吞掉"的位置 | 完成率初定 ≥ 90%；故障注入全部通过；关键路径上吞错为 0 | CO、HO、CI |
| 2 | **说完成就是真完成** | 注入已知缺陷的评测集上，Reviewer 放过了多少、冤枉了多少；每个"完成"能否追溯 | 误放过、误打回初定各 ≤ 10%；每个"完成"都能追溯到审过的改动、判的人和证据 | HO、SC |
| 3 | **不浪费** | 与直接使用同一个编码 Agent 做同一道题对比 | 简单任务耗时 ≤ 直接用 Agent 的 1.2 倍；成功率不低于直接用；每个任务花了多少钱在网页上看得见 | CE、EV、HO |
| 4 | **越用越好** | 同一批没见过的任务，带着积累的经验跑和清空经验跑，各跑一遍 | 至少一个领域，带经验时成功率或成本有统计上站得住的改善 | LE、EV |
| 5 | **谁都能上手** | 一台全新的机器，从安装到拿到第一个结果 | Linux、macOS、Windows 都在 10 分钟内完成，不需要看文档；Mac 安装包已签名；Windows 原生通过核心测试 | UX、CI |
| 6 | **多人用也安全** | 隔离测试与安全审查 | 账号和项目互相隔离并有测试；一个用户的 Agent 读不到别人的文件；安全审查没有高危问题 | SE |
| 7 | **接口稳定，升级不坏** | 领域插件接口与旧数据升级 | 领域 SDK 有公开的 v1 并按版本管理；社区领域对新版本的契约测试通过；0.x 的项目数据能直接升级 | EC、CO、RL |
| 8 | **每次改动都能证明没变坏** | 持续集成与公开评测 | 三个平台每次提交都跑核心测试；类型检查新增问题为 0、核心包清零；每次发布都更新公开对照表 | CI、EV |

## 我们现在在哪

诚实地说，Argus 已经能做很多事，但离上面的标准还有不小的距离。

- **规模**：约 25 万行 Python 和 7.7 万行 TypeScript，857 个测试文件，Linux 上约 12,700 个测试全部通过；
  2,569 次提交，约 20 位活跃贡献者；7 个内置领域，社区仓库另有 24 个。
- **交接和审阅是最常出事的地方**：在完整的开发历史里（包括迁入本仓库之前），提交说明提到 Reviewer 的有 774 个。最近两个实例的 59 次"继续"里，
  30 次是在什么都没变的时候又审了一遍，17 次是 Reviewer 读不到文件或缺工具，只能把活退回去
  （详见 [交接设计](role-handoff-design.zh-CN.md)）。好的一面：试用实例 25 个任务里 22 个通过，13 个一轮就过。
- **结果可信度靠 Reviewer 读叙述**：出现过只算了一段 2048 token 就写成整个数据集困惑度、
  结果打平却写成"达到或超过"、一篇 11 页论文 13 分钟写完且 6 次评审全部通过的情况。
  Reviewer 放过错误的比例从来没测过。
- **比直接用 Agent 慢、贵**：一道修 6 个测试的题，直接用 Copilot 28 秒，Argus 53 秒，
  加上独立 Reviewer 100 秒。试用实例 409 次模型调用花了 88.85 美元，其中 Planner 的调用次数是 Engineer 的两倍。
- **"自进化"还没有证据**：学习流程在跑，但两次实测都没看到任务质量变好。
- **出错容易被吞掉**：代码里有 3,268 个 `try:`、842 个 `except Exception`；类型检查有 1,433 条存量问题（2026-09-12 统计）；
  每次提交只在 Linux 上跑后端测试。
- **上手门槛高**：要先装好并登录一个编码 Agent 命令行工具；Mac 安装包没有签名；网页版所有人共用一把钥匙，
  没有账号；试用中出现过 Engineer 读到另一个租户文件的情况。
- **社区领域依赖框架内部代码**：约 15 个私有模块被社区仓库直接引用，框架一重构就可能把它们弄坏。

### 主题 HO：交接与审阅——让把关的人看到真东西

[对应原则：1、5、8](PRINCIPLES.zh-CN.md)

**现在的问题**：干活的（Engineer）和把关的（Reviewer）靠"传话"协作。把关的人看到的主要是干活的人
写的总结，而不是活本身，还经常读不到该读的文件；结果要么反复打回，要么漏看放行。系统自己有时还会
改写把关人的结论，或者用它的名义记一笔，事后说不清谁说了什么。

**我们要的样子**：像代码评审看 diff 一样，Reviewer 直接看"这次到底改了什么"，而且看的是整个任务的改动；
每条记录写清是谁说的，谁也不改别人的话；没变化就不审；审不了的问题交给能解决的人；系统只管预算和硬规则，
不替模型猜"有没有进展"。完整设计见 [role-handoff-design.zh-CN.md](role-handoff-design.zh-CN.md)。

#### HO-1 交接指标报告
`0.2` · `S` · 依赖：无 · 新人友好
- 现在：没有一个工具能告诉我们"每个通过的任务审了几次、几次是白审"。后面所有改进都需要这个数。
- 要做：在 `argus/tools/` 写一个只读报告，读项目的 `events.jsonl` 和轮次交接文件，输出：
  每个通过任务的 Reviewer 调用次数、其中候选没变化的次数、"继续"的理由分类、耗时、token、模型调用次数。
- 做完的样子：给一份固定的事件日志，测试得到预期数字；本文写明运行命令。
- 可拆成：HO-1a 统计调用次数与耗时；HO-1b 识别"没变化又审"；HO-1c 理由分类（报告用，可以粗分）；HO-1d 命令行与说明。
- 运行：`python -m argus.tools.efficiency_report <项目状态目录> [--json]`（只读；数据只取自 `events.jsonl`，交接文件里的轮次结论事件里都有）。
  另外按角色列出调用、token、缓存读写和花费占比；列出没带来新信息的调用（Planner 只决定继续等、Manager 督导没生效或维持原样、
  后台任务没跑完时的复审）以及因"没变化"省掉的调用；上下文长度分布及随会话轮次的变化；失败和重试的花费。
- 状态：已完成（`7a2432b5`）。

#### HO-2 没变化就别再审一遍
`0.2` · `M` · 依赖：无
- 现在：后台任务还在跑、什么都没变，Reviewer 也被叫来审一次，然后说"再等等"。59 次"继续"里有 30 次是这样。
- 要做：调用 Reviewer 之前（`engineer/round_reviewer.py` 的 `_invoke_reviewer_with_retry`），检查自上次审阅后有没有变化：
  工作区文件、新到的外部结果、操作员的新指令。没有就记一条系统事件，继续等或继续干，不调用 Reviewer。
- 做完的样子：后台任务未完成时测试里 0 次 Reviewer 调用，结果到达后恰好 1 次；HO-1 回放旧日志能看到白审比例下降。
- 可拆成：HO-2a 定义"变化"；HO-2b 调用前检查并记事件；HO-2c 网页显示"等待结果，未重复审阅"；HO-2d 测试。
- 状态：不做了。Engineer 现在在自己的回合里等后台任务跑完再交棒，任务跑到一半就叫 Reviewer 的情况不会再出现；用来跳过 Reviewer 的事实账本已删除。旧任务目录下的 `holders.json` 和旧的跳过事件读到即忽略。

#### HO-3 审不了的问题交给能解决的人
`0.2` · `M` · 依赖：无
- 现在：Reviewer 读不到文件、没有命令行时，只能把活退回给同样无能为力的 Engineer，来回空转（59 次里 17 次）。
- 要做：让 Reviewer 能把障碍上报给系统（缺权限、缺工具）或契约的主人（要求互相矛盾），用 `→ manager` 交过去；
  这种情况下不再重跑 Engineer。Reviewer 现在拥有和 Engineer 一样的工具，审阅需要时它自己跑代码。
- 做完的样子：测试中 Reviewer 报告读不到文件后，任务进入上报，不再有 Engineer 回合。
- 可拆成：HO-3a 上报动作；HO-3b 清理提示词。

#### HO-4 Reviewer 只写了一段话、没点"提交"
`0.2` · `S` · 依赖：无 · 新人友好
- 现在：Reviewer 用文字给了结论但没调用审阅动作，被当成后端故障，连续两次任务直接报错结束。
- 要做：重试时明确告诉它"你没有提交判决"；删掉 `reviewer/_parsing.py` 里已经没人调用的文字解析救援代码。
- 做完的样子：测试中第一次只写文字、第二次正常提交，任务继续而不是报错。
- 状态：文字解析代码已随 HO-16e 删除（`reviewer/_parsing.py` 已不存在）；重试提示还没做。

#### HO-5 Manager 的"等一下"不能把已经通过的结果作废
`0.2` · `M` · 依赖：无
- 现在：Reviewer 已经判了通过，随后 Manager 的等待指令把任务变成暂停，恢复后 Engineer 从第 1 轮重来。
- 要做：在 `engineer/round_settlement.py` 里先把通过的判决结算掉，或者恢复时从它继续。
- 做完的样子：测试中"通过后立即等待再恢复"不会重做已通过的工作。

#### HO-6 "能不能问操作员"只有一个说法，问不到时 Manager 说了算
`0.2` · `M` · 依赖：无 · 进行中
- 现在：Reviewer 的工具说明读环境变量，结算读项目策略；两者不一致时，Reviewer 被引导去问一个结算会拒绝的问题。
  操作员说了"别问我"之后，凭据、花钱、不可撤回操作、发布、模型配置故障这些决定仍然等操作员，或者直接以"需要操作员"结束。
- 要做：所有地方都读同一个生效策略。按原则 8，问不到操作员时（操作员说"别问我"，或运行没有操作员），
  Manager 持有操作员的全部权限：它用类型化字段作答，执行走操作员回答的同一条路径，每个代做的决定都留痕并列入交付报告。
  凭据例外：Manager 拿不出自己没有的凭据，只能决定绕过或结束该项。
- 做完的样子：策略为"禁止提问"时，Reviewer 的工具说明里不再出现"去问操作员"；没有任何代码路径等待操作员或以"需要操作员"结束；
  Manager 只能回答交给它的卡片；交付报告逐条列出它代做的决定。
- 状态：统一判断和 Manager 接手权限都已在 `dev`。原来四种说法（`AUTONOMY_MODE`、`--no-operator`、前门提问策略、
  带 30 分钟计时的 `--operator-wait-exit`）已合成一个开关 `ARGUS_SKILL_OPERATOR_AVAILABLE`；按文字匹配的边界正则已删。

#### HO-7 给 Reviewer 看真正的 diff
`0.3` · `L` · 依赖：无
- 现在：Reviewer 只拿到最多 20 个"最近改过的文件名"，没有内容；`.argus` 下的运行结果完全看不到；
  每次审完就重新计时，所以"通过"只覆盖最后一轮的改动。现有的私有快照功能默认关闭、触发不了、也没人读。
- 要做：
  - HO-7a 快照存储：在项目状态目录下放一个私有仓库，把工作目录做快照；跳过生成物、虚拟环境、嵌套仓库，
    大文件只记路径、大小和修改时间；绝不碰用户自己的仓库。实测在最大的线上项目（220 GB）上首次 3.7 秒，之后每次 0.03 秒。
  - HO-7b 审阅输入：任务开始时拍"基线"，每次请求审阅时拍"候选"，先给 Reviewer 看基线到候选的改动、命令记录，
    再看 Engineer 的说明；替换 `roles/prompts/reviewer.py` 的 `_changed_artifact_block`。
  - HO-7c 绑定：只有通过时基线才前移；判决记下它审的是哪个候选，阶段证书和回放只对这个候选有效。
  - HO-7d 删除旧的 `skills/round_checkpoint.py`、开关 `ARGUS_SKILL_ROUND_CHECKPOINT` 和按修改时间计算的窗口。
- 做完的样子：非 git 目录、git 目录、嵌套 `.git`、大文件、排除目录都有测试；"通过"覆盖整个任务的改动。
- 状态：HO-7a、HO-7b 已完成（`247b432c`），按修改时间计算的窗口已随之删除；HO-7d 已完成（轮次检查点和它的开关已删除）；HO-7c 待做。

#### HO-8 谁说的话记在谁名下
`0.3` · `L` · 依赖：无
- 现在：有 4 处系统代码会直接改 Reviewer 的判决；判决来源默认写成"reviewer"，查不清时就算 Reviewer 说的；
  给 Engineer 的下一步指令有 5 个地方在写。
- 要做：
  - HO-8a 新增"系统干预"记录，引用它影响的判决；结算由"判决 + 干预"算出最终结果，并记录两边输入。这一步不改行为。
  - HO-8b～8d 把 venue 验收、后台任务等待、操作员提问策略这三处改写，分别改成干预记录。
  - HO-8e 去掉"默认是 reviewer"的写法，作者不明时明确报错；合并重叠的来源字段。
  - HO-8f 下一步指令只有一个写入者。
- 做完的样子：架构测试禁止系统代码改 Reviewer 判决的字段；封存的记录里 Reviewer 原话和系统干预分开存放。

#### HO-9 按验收标准逐条判
`0.3` · `M` · 依赖：无
- 现在：验收标准散落在任务目标、原始请求、目标契约、阶段指引里；Reviewer 的结论是一段自由文字，和标准没有对应关系。
- 要做：会产生结论的工作，Planner 必须写验收标准；通过和打回都逐条标注每项标准的状态；标准之外的新问题记为
  "后续事项"交给 Planner，不阻断（触及真实性底线的除外）；Reviewer 直接引用任务契约，不再读拼接出来的目标；
  把从未合入 `dev` 的 `fix/completion-objective-status`（目标是否达成）重新合入。
- 做完的样子：漏掉任何一条标准的"通过"会被工具拒绝；后续事项不阻断也不丢。

#### HO-10 checkpoint 的说法前后一致
`0.3` · `S` · 依赖：无 · 新人友好
- 现在：Engineer 被要求把证据路径写进 `CHECKPOINT.md`，Reviewer 被要求别读它，会话轮换的提示又让 Reviewer 参考里面的批准。
- 要做：证据应在工作区里（HO-7 之后在 diff 里）；统一提示词；删除 `shared_checkpoint_instructions` 里没被用到的 Reviewer 分支。

#### HO-11 Engineer 的决定别显示错
`0.3` · `S` · 依赖：无 · 新人友好
- 现在：显示已改正（fix/liveness-adopt）："卡住了"不再显示成"继续"，默认交给 Reviewer 时也显示"交给 Reviewer"。

## 1.0 之后：远景

正式版解决的是"可靠、可信、好用"。在那之后，Argus 想去更远的地方：

- **团队科研工作台**：多人在同一个项目里协作，评论、分工、共享经验（UX-12、SE-7）。
- **跨领域的大任务**：一个目标同时调动多个领域，例如"做一个新内核，写成论文，并发布成开源库"（EC-7）。
- **能独立验证的科研成果**：在数学方向，对一个公开难题给出可机械核验的证明或反例；在机器学习方向，
  产出能被外部团队一键复现、并被同行评审接受的论文（RA-3、RA-4、RA-9、SC-6）。
- **公开的自我改进记录**：每个领域一条持续更新的"越用越好"曲线，以及与直接使用 Agent 的公开排行榜（LE-8、EV-2）。
- **开放的领域市场**：社区按 SDK 发布领域，有兼容矩阵、评分和下载量（EC-3、EC-9）。
- **TypeScript 运行时**：调度和状态迁到 TS，Python 作为插件运行（TS 主题）。

## 如何参与

1. **先找一件事。** 想快速上手，可以从标了"新人友好"的任务开始，例如 HO-1、HO-4、CI-1、CO-1、SC-9、SC-14、
   LE-5、RL-4、UX-3、RA-8。
2. **说一声。** 在 issue 或 draft PR 里写上任务编号，避免两个人做同一件事。L 级任务请先在 issue 里说明拆分方案。
3. **从 `dev` 开分支。** 分支名用 `fix/<编号>-<简述>` 或 `feat/<编号>-<简述>`，PR 提到 `dev`，详见
   [CONTRIBUTING.md](../CONTRIBUTING.md)。
4. **说明为什么。** 在 PR 描述里写这项改动服务 [原则](PRINCIPLES.zh-CN.md) 中的哪一条。说不出原则的新机制不进入 Core。
5. **先写会失败的测试。** 加一个改动前失败、改动后通过的测试；运行任务里提到的测试和完整的 Python 测试套件。
6. **关于发行清单。** 只改 Python 时，发行清单会过期，`tests/release_tools/test_check_artifacts.py` 会提示，
   直到运行 `python -m argus.release_tools.build_release`；请在 PR 里说明是否运行过。改了前端源码必须一起提交重新构建的界面。
7. **一个 PR 一件事。** 不要在同一个补丁里同时改接口、存储格式、阶段语义和部署方式。旧数据必须仍然能读，
   已经在运行的任务按它开始时的规则完成。
8. **做完更新本文。** 在任务旁标注状态和对应的 PR；如果实测结果改变了某个目标数字，一并更新。

# Argus 原则

这不是 checklist，也不是某次事故的修复清单。原则必须在模型、领域、任务和实现变化后仍然
成立，并能推导具体设计；如果一条规则只解释某个字段、Gate 或文件，它是策略或机制，不是原则。

Argus 只保留九条上位原则。新增机制必须能说明自己由哪条原则推出；不能说明，就不该进入 Core。

英文版：[PRINCIPLES.md](PRINCIPLES.md)

## 1. 语义判断属于 Agent，机械事实属于 Runtime

价值、路线选择、优先级、完成质量和一段证据意味着什么，需要完整语境，应由 Agent 判断。
进程是否退出、文件是否存在、预算是否超限、路径由谁占用、动作是否不可逆，是机械事实，应由
Runtime 保证。

Runtime 向 Agent 提供它无法直接感知的事实，但不通过正则、计数器、固定阈值或 schema 偷做
科研判断。Agent 也不能靠散文绕过权限、预算、并发和真实性边界。一项能力不能依赖某台开发机
被人手工准备好的环境；Runtime 必须发现宿主能力，并自行建立项目本地、可复现的环境，或者明确
报告该能力不可用。预装 venv、缓存、路径、凭据和某个人的 shell 配置都不是产品能力。

## 2. Core 提供能力，Vertical 提供领域政策

Core 是稳定的小内核：执行、持久化、调度、权限、通信、可观测性和版本化扩展接口。Vertical
定义领域的 stages、Skills、工具、证据含义、评审标准和完成语义。

Core 不导入具名 Vertical，不认识某个会议、数据集、定理或实验门槛。内置 Vertical 与外部
Vertical 必须通过同一接口加载；更换或新增领域政策不应要求修改 Core。Vertical 声明需要什么，
Core 的环境 adapter 负责在当前宿主发现、准备或拒绝这些能力，Vertical 不能写死某台机器的路径
和预装环境。

## 3. 思考用自然语言，副作用才需要最小协议

角色用自然语言推理和交接，共享目标、策略、证据与未解决问题。不能为了方便解析而要求模型把
思考压成 JSON、固定表格或大段键值对。

只有 Runtime 必须无歧义执行的副作用才使用类型化字段，例如目标 owner、路径所有权、生命周期
动作和不可逆授权。协议应尽可能小；格式错误不能抹掉已经理解的工作。旧格式可以兼容，但不能
继续支配新 Prompt。

## 4. 每个 Token 都应购买信息或行动

模型调用必须至少完成一件事：改变真实 artifact、改变策略、减少关键不确定性，或提供无法由
现有证据推出的独立判断。复述上下文、重填 schema、重复 unchanged checks、为 UI 重新裁决、
以及对未变化的 artifact 反复评审，都不是工作。

确定性事实交给工具；上下文按引用和 delta 共享；默认选择能完整拥有任务的最短角色链。只有当
并行搜索或独立判断会改变结果时，才增加 Agent。Token 效率以任务成功、质量、墙钟、模型调用、
工具调用和追问次数衡量，不以 Prompt 是否短或缓存命中率单独衡量。

## 5. 探索优化上限，声明接受证据约束

探索阶段应主动搜索、组合不同机制、追逐高信息增益和高潜在收益，允许推测、报告型研究、
未实现想法与失败 prototype。真实性底线始终存在，但最终交付标准不决定一个想法是否值得探索。

只有声明才需要与声明规模匹配的实现忠实度、可信参照、直接证据和独立评审。任何被作为确定结果
交给用户、写入最终 artifact，或用于授权下游决定的内容，都已经是声明，不能继续借“探索”豁免。
评审针对冻结的候选 artifact 做一次决定；仪式化 Gate、重复认证和文件数量不能替代直接证据。

## 6. 失败是更新策略的信息，不是自动生成的产品

一次负结果首先要区分 setup、实现、优化、数据、规模、evaluator 和方法本身。只要仍有高价值
修复或替代路线，失败就应驱动下一轮工程与策略，而不是被迅速包装成最终交付来结束任务。

这不意味着隐藏负结果。只有当负命题本身重要、事先界定、实验有能力检出目标效应，并排除了
最强替代解释时，负结果才可以成为最终贡献。否则它是诚实的中间反馈。

## 7. 优化 Programme，而不是完成任务队列

目标是用户要的最终能力、发现或论文，不是让 backlog 变绿。任务、计划、方法名和 stage 都是
可替换手段；如果局部进展不再改变最终结论，就应重构路线，而不是继续在邻域爬山。

daemon 活着、论文变长、图变多、Gate 通过和 mission 完成，都不是独立的进展指标。真正的进展
是提高最终结果、降低关键不确定性，或做出能改变全局策略的判断。Manager 维护 programme
视角，Planner 只生成能推动它的工作。

## 8. 自治由可逆性决定

本地、可逆、预算内的行动默认由 Agent 自主完成，包括读取、调研、实现、测试、隔离依赖和可撤销
实验。只有凭据、支付、外部发布、破坏性删除、全局基础设施变更和其他不可逆权限需要人类。
环境准备默认发生在项目本地或隔离容器中；Argus 不能假设管理员权限，也不能为了让一个任务可跑
而修改整台机器的全局工具链。

提问是最后手段，不是风险转移工具。Reviewer 的独立性用于重要声明和真正需要第二判断的工作，
不是给每个局部动作增加许可层。

## 9. 自进化只由端到端结果证明

Argus 对自己的修改必须像产品实验一样接受真实用户任务和匹配对照。内部 Gate 通过率、事件数、
任务数和自评文字都不能证明系统变好。

比较必须同时观察成功率、最终质量、墙钟、Token、模型调用、工具调用、追问、恢复能力和成本。
生产反馈进入下一轮设计，但不能让正在被评估的系统自己选择最有利的评分口径。依赖环境的能力
还必须在干净安装或等价的冷启动环境中复现；在一台长期手工维护的服务器上成功不算可移植性证据。

## 从原则推导策略

下面这些是当前合理的策略，但它们不是永恒原则：

- Core/Vertical 分库，由原则 2 推出；
- 自然语言交接和最小 footer，由原则 1、3 推出；
- direct 短链、按需 Skills、共享 mission view，由原则 4 推出；
- explore/develop/certify 分层，由原则 5 推出；
- 负结果继续优化或全局换路，由原则 6、7 推出；
- 最终冻结候选的一次独立 Reviewer，由原则 5 推出；
- 少问操作者、允许 Agent 自主安装本地隔离的项目依赖，由原则 8 推出；
- 自动发现 CUDA/driver/磁盘/调度器，创建锁版本的项目环境并做单 batch smoke，由原则
  1、2、8、9 推出；
- Argus 与直接 Agent 的同题对照实验，由原则 9 推出。

实现可以替换，只要仍满足原则。实现与原则冲突时，修改实现，不增加例外条款。

## 五个设计自检问题

1. 这是语义判断，还是 Runtime 才能知道的机械事实？
2. 这是领域政策，还是所有 Vertical 都需要的通用能力？
3. 这个格式是否真的对应机器副作用，还是只为了让模型更容易被解析？
4. 这次模型调用会改变 artifact、策略、关键不确定性或独立判断吗？
5. 这项工作会推动 programme 的最终结果吗？

任何机制如果连续答不清这五个问题，就应删除，而不是再加一层来保护它。

用好 Argus

跑通第一个任务之后，决定结果好坏的主要是四件事：目标写得清不清楚、什么时候插话、用什么模型、花多少钱。每一条都配了 Argus 真实项目里的例子。

怎么写目标

Manager 会把你的话整理成一份任务契约：目标、范围、完成标准、不做什么、可以动哪些路径。你写得越清楚，这份契约就越准，后面需要它停下来问你的次数就越少。

三件事一定要写

  1. 要什么：交付物是什么，而不是“帮我研究一下”。
  2. 怎样算完成：能检查的标准。测试通过、指标达到、对比用的是哪个基线。
  3. 不许做什么：不能换的模型、不能动的目录、不能引入的依赖。
模糊
帮我把这个模型的推理优化一下。
清楚
把 model/ 的推理延迟在单张 A6000 上降 20% 以上。
基线：当前 main，batch=1，同一组 100 条输入，各跑 10 次取中位数。
质量：输出与基线逐条比对，不允许下降。
不许：换更小的模型、用多卡、改 data/。

把“不许缩小任务”写进去

Agent 最常见的偷懒方式，是悄悄把任务变小：换个小模型、少跑几轮、用估算代替实测，然后报告“完成了”。在目标里直接写明不允许这样做，同时告诉它做不到时怎样算合格的结果，它就不会为了交差硬凑。Argus 自己的长任务目标就是这么写的：

If RTX 5090 is infeasible because of memory, operators, or software support,
“infeasible, with evidence and minimum viable requirements” is a valid result.
Never silently switch to a smaller model, omit checkpoint components, or use
multiple GPUs while claiming single-GPU success.

长任务：用一份完整的任务书

要跑好几天的任务，建议一次发一份结构化的任务书，而不是零散地聊。仓库里的 ARGUS_IMPRESSIVE_RESULTS.md 有多份可以直接照抄的范本，结构都是：

段落写什么
开头一句这是一个长期任务，测到新数据可以改计划；不要只交一个计划就停，做到完成或者说清楚卡在哪、需要我做什么。
MISSION要交付的成果，以及用什么来评判（比如端到端延迟和质量，而不是某个微基准）。
EXECUTION PATH先做什么、后做什么，每一步的进入条件。
DECISION RULES遇到岔路时怎么选，哪些结论算无效。
REQUIRED DELIVERABLES冻结的基线、重复测量的结果表、一句话的结论，以及结论的适用范围。
小技巧

不确定自己写得够不够清楚，可以在终端驾驶舱里用 /rewrite 你的目标 让 Manager 先帮你改写一遍再发；用 /plan 你的目标 先看 Planner 会怎么拆，再决定要不要真的开工。

中途插话、改方向

你说的每一句话都先到 Manager。它会判断：自己直接回答、只读地查一下，还是交给团队去做。暂停、中止、授权这类控制指令走单独的通道，不会被当成新任务。正在跑任务时再交新任务，会排在当前任务后面。

你想……终端驾驶舱说明
补充一个要求/nudge 文字把指导塞进正在跑的任务，不打断它
只问问题/ask 问题Manager 直接回答，不排任务，不惊动 Planner / Engineer / Reviewer
先看看计划/plan 目标预览 Planner 的执行计划
直接排一个任务/task 文字跳过对话，直接进待办
停掉某个任务的自动迭代/stop 编号不删除任务
立刻停下当前任务/abort中断正在跑的任务
看完整的任务契约/item 编号目标、范围、完成标准都在里面

在网页驾驶舱里，直接在对话框说同样的话即可，比如“暂停一下”“现在在干什么？”“换成 copilot 后端”。

什么时候该插话

  • 它在问你。默认的 pragmatic 模式下，Argus 只在这几种情况停下来问：需要凭据、要多花钱、不可撤销或对外的操作、要改你定下的完成标准。看到提问就及时回，回得越快它闲着的时间越短。
  • 你知道它不知道的事。比如“这台机器 GPU0 被别人长期占着”“那个数据集的标签有问题”。这种信息越早给越省事。
  • 方向明显偏了。先 /nudge 说清楚为什么偏、要回到哪里；改动大到要换目标时，/abort 之后重新交一份目标，比在原任务上反复打补丁干净。

不需要插话的情况：超时、测试失败、换技术路线、调基准规模。这些在 pragmatic 模式下它会自己处理。

调整它多久问你一次

$ export ARGUS_SKILL_AUTONOMY_MODE=cautious     # 每个明确的问题都问你
$ export ARGUS_SKILL_AUTONOMY_MODE=pragmatic    # 默认：技术问题自己恢复
$ export ARGUS_SKILL_AUTONOMY_MODE=autonomous   # 可撤销的操作尽量自己做

不论哪种模式，凭据、付款、不可撤销的操作和对外发布都一定会停下来等你。

安全地停下来

$ argus --status                    # 看后台和待办
$ argus --daemon-stop --drain       # 推荐：等当前任务到自然边界再停
$ argus --daemon-stop --force       # 强制：会打断正在跑的任务

关掉驾驶舱不会停掉后台工作；你主动暂停的任务也不会被记成“失败经验”。

选后端和模型

Argus 支持 codex、claude、copilot、cursor、opencode、pi、grok、qoder、dsh。不知道选哪个时，选你平时已经在用、已经登录的那个，不用为 Argus 再开账号。

$ argus --setup --backend claude        # 换后端，并真实跑一轮确认
$ argus --config-help                   # 每个角色实际用的后端、模型及来源

在驾驶舱里也能直接换：终端用 /backend copilot，网页上说“把模型换成 claude-sonnet-5”。

不同角色用不同模型

四个角色的分工不同，默认的思考强度也不同：Engineer 是 xhigh，Manager、Planner、Reviewer 是 high。需要时可以单独给某个角色指定模型或后端：

$ export ARGUS_SKILL_MODEL=auto                  # 所有角色共用，auto = 后端自己的默认
$ export ARGUS_SKILL_ENGINEER_MODEL=...          # 只改 Engineer
$ export ARGUS_SKILL_REVIEWER_BACKEND=claude     # 让 Reviewer 用另一家后端
建议

让 Reviewer 和 Engineer 用不同家的模型，审查会更独立，一个模型的盲点不容易被另一个同款模型放过。

用 Pi 或 OpenCode 这类可以接多家供应商的 CLI 时，要说明用哪家：OpenCode 必须设 ARGUS_SKILL_OPENCODE_PROVIDER，否则配置的模型不生效。细节见 后端与模型供应商。

控制花费

Argus 会一直干到完成为止，所以上限要你自己定。最常用的几个旋钮：

配置项默认作用
ARGUS_SKILL_GLOBAL_DAILY_CAP_USD1000每天全局花费上限（美元）。到了上限任务会暂停，提高上限或到第二天会自动继续
ARGUS_SKILL_GLOBAL_DAILY_TOKEN_CAP0（关）每天全局 token 上限
ARGUS_SKILL_CODEX_DAILY_CALL_CAP300Codex 每天调用次数上限
ARGUS_TEAM_DEFAULT_WIDTH2一个任务默认同时开几个 Engineer
ARGUS_TEAM_MAX_TOTAL_IN_FLIGHT2全局最多同时在跑的队员数
ARGUS_SKILL_MAX_ROUNDS0（不限）一个任务最多跑几轮

这些都可以在 argus --config-help 里看到当前值，也可以在驾驶舱里用 /config key=value 修改。

注意
  • 供应商的计费数据是异步回来的，所以实际花费可能略微超过上限，不会差太多。
  • 查不到价格的调用默认会被拦下（ARGUS_SKILL_UNPRICED_COST_POLICY=block），不会被当成免费。
  • 账目记在 Argus 数据目录的 cost-control.json 和项目的 usage.jsonl 里，不要删。

省钱的习惯

  • 简单问题用 /ask，它只让 Manager 回答一次，不会拉起整个团队。
  • 第一次跑新类型的任务，先把每日上限调低，看一天的花费曲线再放开。
  • 并行宽度不是越大越好：同时跑的 Engineer 越多，花费成倍增加；资源（比如 GPU）不够时它们还会互相抢。

什么任务适合交给 Argus

Argus 是为长时间、需要审查的自主工作设计的。在 27 个长期任务、累计 1,548 小时的运行里，它平均约 310 小时才需要人做一次决定。

适合
  • 有明确评判标准、要反复实验的研究和优化：训练、调参、性能优化、复现论文。
  • 要跑好几个小时甚至几天、你不想一直盯着的工程任务。
  • 需要“做完还要有人审”的结果：结论要有证据、数字要能追到日志。
不太适合
  • 一句话就能答的问题。用 /ask，或者直接问你的 Agent CLI。
  • “好不好”完全取决于你个人口味、又说不出标准的任务。
  • 必须由人负责的动作：付款、对外发布、不可撤销的操作。Argus 会停下来把这些交还给你。

真实项目里的例子

先怀疑实验设置，再怀疑模型

一次复现里，MATH-500 测出 6.0%，而公开结果是 79.7%，这个数字差点被当成“边界结果”写进论文。原因是生成长度被限制在 12 个 token，测的是这个上限，不是模型。放开上限后到了 68.8%，再按公开协议调用它假定的工具，到了 76.4%。

给你的启发：目标里写上“和公开数字差距很大时，先排查设置”。Argus 现在内置了一条 suspect-the-setup skill 专门处理这种情况。（来源：failure-modes-and-fixes.md）

敢于放弃走错的路线

FlashDA 把六种扩散语言模型的掩码移植进 FlashAttention-4 内核，最后在 H200 上达到原生 FA4 的 92–95%。但最初的路线比原生慢 4.9–29.6 倍，是认识到数据通路选错并放弃它，才有了后来的结果；被放弃的路线和证据也都保留了下来。全程 21.85 小时模型计算，花费不到 80 元。

给你的启发：目标里允许“推翻自己的路线”，并要求保留被否定的路线和证据，比只要一个漂亮数字更容易得到真结果。（来源：README）

把结论的范围写窄

Argus 的成果记录里，结论只覆盖实际测过的硬件、形状、重复次数和审查状态；查不到原始来源的 3.92× 和 4.52× 已经被删掉，没被合并的 PR 也如实写成“已关闭，未合并”。

给你的启发：在完成标准里要求“一句话结论 + 适用范围 + 已知例外”，你拿到的结果才能放心转述给别人。

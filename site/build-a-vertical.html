建自己的纵向

纵向就是你把某个领域的经验教给 Argus 的方式：这类工作分几个阶段、每个阶段怎样算做完、做事和审查时该凭什么判断。本页带你从零做一个真实可用的小纵向 data_report，最后发布到纵向商店，让别人一条命令就能装上。

纵向是什么

Argus 的核心只管调度和记账，领域的事都归纵向：阶段、skill、工具、证据的含义、审查标准、怎样算完成。Argus 自带 7 个纵向（research、software、math 等），社区仓库里还有十几个（诗词、芯片设计、量化、医学……）。Manager 收到任务后，会挑最合适的纵向来做。

阶段
这类工作按什么顺序推进，每个阶段要交出什么证据。
skill
一篇篇 Markdown，告诉做事和审查的角色该凭什么判断。
路由
一句用途说明和分类路径，让 Manager 知道什么时候该用你。

一个最小的纵向只要 一个 Python 文件加几篇 Markdown。完整的例子在仓库的 docs/examples/verticals/data_report/，下面每一步都对应其中的文件。

开始之前

先按快速上手装好 Argus 并跑通一个任务。下面的命令里，argus 和 python 都指装 Argus 的那个环境，Linux 上就是 $HOME/Argus/.venv/bin/ 里的。

1想清楚“做完”是什么样子

先别写代码。拿一张纸回答三个问题，这比后面所有步骤都重要：

问题data_report 的答案
这个领域的任务长什么样？给一份表格数据，写出一份分析报告。
老手做这件事分几步？先摸清数据 → 再分析 → 最后写报告。
每一步做到什么程度才算数？拿什么证明？报告里的每个数字都能用项目里的脚本重新算出来。证据是脚本、命令和保存下来的输出。

第三个问题的答案就是这个纵向的灵魂。说不清楚的话，先去看看你所在领域里，好的成果和糊弄的成果到底差在哪。

2建目录

纵向的名字只能用小写字母、数字和下划线，以字母开头，而且不能和自带的纵向重名。目录结构是固定的：

data_report/ # 这一层是一个可安装的 Python 包 ├── pyproject.toml # 声明入口点，让 Argus 找到你 ├── vertical.json # 发布到商店时用的清单 └── argus_verticals/ # 命名空间，不要放 __init__.py └── data_report/ ├── __init__.py ├── stages.py # 阶段、检查项、路由 └── skills/ ├── engineer/ │ └── data-report-analysis.md └── reviewer/ └── data-report-review.md
$ mkdir -p data_report/argus_verticals/data_report/skills/{engineer,reviewer}
$ cd data_report
$ echo '"""Data report vertical."""' > argus_verticals/data_report/__init__.py

然后写 pyproject.toml。最关键的是 argus.verticals 这个入口点，Argus 就是靠它找到你的纵向：

[build-system]
requires = ["setuptools>=68"]
build-backend = "setuptools.build_meta"

[project]
name = "argus-vertical-data-report"
version = "0.1.0"
requires-python = ">=3.11"

[project.entry-points."argus.verticals"]
data_report = "argus_verticals.data_report.stages"

[tool.setuptools.packages.find]
include = ["argus_verticals*"]
namespaces = true

[tool.setuptools.package-data]
"argus_verticals.data_report" = ["skills/**/*.md"]

3写 stages.py：阶段和检查项

纵向不需要继承任何类，stages.py 里的几个模块级变量就是全部约定。把第 1 步纸上的答案原样翻译过来：

from pathlib import Path

from argus.skills.stage_machine import ChecklistItem

ARGUS_VERTICAL_API_VERSION = 1
VERTICAL_PURPOSE = (
    "Turn one tabular dataset (CSV, Excel, Parquet) into a short analysis report "
    "whose every number can be recomputed from a script in the project."
)
VERTICAL_ROUTING_PATH = ("analytics", "data", "report")
VERTICAL_SKILL_PARENTS = ()
VERTICAL_SKILLS = Path(__file__).resolve().parent / "skills"

CHECKLIST_STAGE_ORDER = ("understand", "analyze", "report")
CHECKLIST_ITEMS = {
    "understand": (
        ChecklistItem(
            "understand.data_profile",
            "The dataset's rows, columns, types, missing values and obvious errors are described from the real file.",
            "a profiling script and its saved output",
        ),
    ),
    "analyze": (
        ChecklistItem(
            "analyze.reproducible_numbers",
            "Every number the report will quote is produced by a script that runs end to end on the original file.",
            "the analysis script, the exact command, and its saved output",
        ),
    ),
    "report": (
        ChecklistItem(
            "report.claims_traced",
            "Each claim in the report names the number, the script output it comes from, and its limits.",
            "report.md with a reproduction section",
        ),
    ),
}
completion_gate = "none"
# One dataset and one report is a bounded analyze-check-revise task, so it keeps
# the framework defaults, written out: the progress window opens after round 12,
# an explicit progress judgement is required from round 24, and four consecutive
# no-progress verdicts end the mission.
ROUND_POLICY = {
    "stall_threshold": 4,
    "no_progress_threshold": 2,
    "soft_round_limit": 12,
    "hard_escalate_rounds": 24,
}


def role_banner(role: str) -> str:
    common = "DATA REPORT: every number must be recomputable from a script in this project."
    if role == "reviewer":
        return common + " Rerun the scripts and compare their output with the report before approving."
    return common

每个字段在干什么

字段说明
ARGUS_VERTICAL_API_VERSION必须是 1，否则不会加载。
VERTICAL_PURPOSE一句话用途。Manager 主要靠它判断什么任务该交给你，写清楚什么时候该用。
VERTICAL_ROUTING_PATH分类 / 领域 / 细分。领域和细分用下划线连起来必须等于纵向名：data + report = data_report。
CHECKLIST_STAGE_ORDER阶段顺序，不能重复。
CHECKLIST_ITEMS每个阶段的检查项：ChecklistItem(编号, 要满足的陈述, 证据提示)。编号在阶段内唯一。
completion_gatenone、metric 或 certified。不确定就用 none。
VERTICAL_SKILLSskill 目录。通过 pip 安装时要写；从商店安装时会自动用 stages.py 旁边的 skills/。
ROUND_POLICY四个轮次守卫：连续几轮没进展算卡住、多少轮后开始判断进展等。发布到社区仓库时必须写，并用注释说明为什么这样取值；当前 Argus 本地运行时会忽略它。有边界的任务用默认的 4 / 2 / 12 / 24 即可。
role_banner(role)可选。给每个角色的一句最高原则。
检查项写陈述，不写数量

好的检查项描述一个可以核实的事实（“每个数字都能由脚本复算”），并告诉审查者去哪里找证据。不要写“至少 3 张图”“报告 500 字以上”这种配额，Agent 很擅长凑数。

4写 skill：教判断，不下结论

skill 是放在 skills/<角色>/ 下的 Markdown，角色目录可以是 manager、planner、engineer、reviewer。开头的 frontmatter 只有两个字段：name 和 description。Agent 需要时会自己去读。

---
name: "Data Report Analysis"
description: "How to analyze one dataset so that the report's numbers can be trusted and recomputed."
---
# Data report analysis

Look at the data before you summarize it. Open the real file, count rows, and
read a sample of raw values; profiling output you have not looked at is not
understanding.

When a number surprises you, suspect the pipeline first: an encoding, a wrong
delimiter, duplicated rows, a unit mismatch, or a filter that silently dropped
data explains more surprises than a real effect does.

Choose the analysis by the question the operator asked, not by habit. A mean
is the wrong summary for a skewed column; a correlation says nothing about
cause. Say why the method you chose fits this data.

Keep every quoted number reproducible: write it from a script, save the output,
and reference that output in the report. If a number cannot be recomputed, do
not report it.

Report what the data cannot answer. Missing segments, small samples, and
measurement limits belong in the report as plainly as the findings do.

审查用的 skills/reviewer/data-report-review.md 结构一样，核心只有一句：重新跑脚本，把输出和报告里的每个数字对一遍。完整内容见例子目录。

为什么写判断依据，而不是规则

配额式规则
- 摘要必须 5 句话、不超过 170 词
- 每张图的说明里必须有数字
- 至少比较 3 个基线
判断依据
- 结论决定篇幅，没有固定配额
- 数字出现在读者需要它的地方
- 选和你的结论真正竞争的基线，
  并说明为什么是它们

这不是理论。Argus 的研究纵向以前用左边那种配额规则写论文，结果摘要变成了“数字墙”。2026 年 9 月 6 日改成右边那种判断式指导后，审查者按目标会议审稿人的标准来判断，而不是逐条核对配额。

  • 讲为什么：告诉它这件事在你的领域里为什么重要、通常错在哪里。
  • 不替它下结论：“均值对偏态数据不合适”是判断依据；“一律用中位数”是替它下了结论，遇到例外就会错。
  • 少而精：每一篇都要能指出它在哪种真实情况下帮上了忙，说不出来就删掉。

5本地装上并检查

把纵向以可编辑模式装进装 Argus 的那个环境，之后改 stages.py 或 skill 不用重装。

$ "$HOME/Argus/.venv/bin/python" -m pip install -e .
$ uv tool install --force --python 3.12 \
    "argus @ https://github.com/microsoft/ArgusAgent/archive/refs/heads/main.zip" \
    --with-editable .
PS> py -m pip install -e .

然后确认 Argus 认出了它：

$ argus verticals list
$ argus verticals info data_report
你应该看到（真实输出节选）
data_report   package   -   -   yes   -   Turn one tabular dataset (CSV, Excel, Parquet) into a short ...

name          data_report
kind          package
enabled       True
routing_path  analytics, data, report
列表里没有它？

导入失败或不符合约定的纵向会被跳过，原因写在服务日志里的一条警告中，警告会点名是哪个纵向。最常见的原因：ARGUS_VERTICAL_API_VERSION 不是 1、VERTICAL_PURPOSE 为空、路由路径拼起来不等于纵向名、名字和自带纵向重复、某个必需阶段没有检查项。

6用它跑一个真实任务

重启驾驶舱，让它读到新纵向。准备一份真实的 CSV 放进练习目录，然后交一个任务：

用 data_report 纵向分析 sales.csv：
各地区的月度销售额趋势如何，哪个地区下滑最明显、可能的原因是什么。
完成标准：report.md 里每个数字都能用项目里的脚本重新算出来，并写明数据回答不了的问题。

Manager 一般会根据用途说明自己挑中你的纵向。第一次测试时在任务里点名，可以排除“没被选中”这个变量。选中的纵向记在项目的 .argus/PIPELINE_STATE.json 里。

检查这几件事
  • 地图上的阶段是 understand → analyze → report。
  • Engineer 先看了真实数据，而不是直接开始画图。
  • Reviewer 真的重跑了脚本。如果它只读了报告就放行，回到第 4 步把审查 skill 写得更明确。
怎么迭代

每发现一次 Argus 做偏了，先问：是阶段的证据要求不清楚（改 stages.py），还是缺了一条判断依据（加或改 skill）？一次只改一处，再跑一次，才看得出是哪处改动起了作用。

7发布到纵向商店

纵向商店读的是社区仓库 Argus-AiTeam/argus-verticals 的发布清单。别人装你的纵向不需要 pip，只要一条命令，桌面版和网页版也能用。发布流程就是往这个仓库提一个 PR。

1) 把纵向放进社区仓库

Fork 并克隆社区仓库，然后：

  1. 把你的 argus_verticals/data_report/ 整个目录复制到仓库的 argus_verticals/ 下。
  2. 在目录里加一份 README.md：这个纵向做什么、不做什么、和哪个相邻纵向的区别。
  3. 在目录里加 vertical.json（见下）。
  4. 在仓库根目录的 pyproject.toml 里，照着已有条目注册入口点：data_report = "argus_verticals.data_report.stages"。
  5. 给你写的每个确定性检查（如果有）在 tests/ 下加测试。
  6. 运行 python scripts/build_catalog.py 重新生成 catalog.json。

不知道怎么写的地方，照着仓库里已有的纵向抄，比如 argus_verticals/materials/。

{
  "name": "data_report",
  "module": "argus_verticals.data_report.stages",
  "version": "0.1.0",
  "purpose_zh": "把一份表格数据变成一份每个数字都能复算的分析报告。",
  "paths": ["argus_verticals/data_report"],
  "requires": [],
  "shared": [],
  "python_requirements": ["pandas>=2"],
  "tags": ["data", "analysis", "report"],
  "maintainers": ["your-github-id"]
}
字段说明
name / module纵向名，以及 stages.py 的模块路径
version语义化版本。修文字是补丁号，加检查项或 skill 是次版本号，改阶段或交付物是主版本号
requires / shared依赖的其他社区纵向和共享代码，必须和代码里实际 import 的一致
python_requirements需要的 Python 包。只展示给用户、不会自动安装，装不装由用户决定
tags2 到 4 个标签

英文用途说明只写在 stages.py 里，不要重复写进清单；skill 父级、API 版本也会自动从 stages.py 读出。

2) 提 PR 前先过检查

在社区仓库的根目录：

$ pip install "argus @ git+https://github.com/lbx154/Argus.git@main"
$ pip install -e ".[dev,zh-fold]"
$ ruff check argus_verticals tests scripts
$ python scripts/build_catalog.py --check
$ pytest -q

都通过后，向 main 提 PR，写清楚这个纵向做什么、刻意不做什么、你是怎么测试的。第 6 步那次真实运行就是最好的测试说明。

社区仓库的规矩
  • 约定一致性测试是门槛：它会导入每个入口点，检查 API 版本、用途、skill 目录，并要求有 README 和入口点注册。不过的 PR 不会进入审查。
  • 纵向之间不能互相 import，除非通过写在 README 里的共享模块或父依赖。
  • 不要提交密钥，也不要提交大数据集；测试数据用手写的小样本。
  • 永远不要为了让测试通过而放宽阈值。

以 CONTRIBUTING.md 的最新版本为准。

3) 合并之后

维护者打出新的版本标签后，CI 会把每个纵向打成 zip，连同带校验值的 catalog.json 一起发布。之后任何人都可以：

$ argus verticals refresh               # 拉取最新的商店清单
$ argus verticals install data_report   # 下载、校验、解压，依赖的纵向会一起装上
$ argus verticals info data_report

网页驾驶舱的“纵向”页面上也能浏览、安装、启用和停用。装好的纵向在 ~/.argus-skill/verticals/argus_verticals/data_report/，Argus 会像对待自带纵向一样发现它。

字段速查

上面没用到、但以后可能用得上的可选字段：

字段用途
VERTICAL_SKILL_PARENTS直接复用另一个纵向的 skill（只复用知识，不继承流程）
WORKFLOW_PROFILES给小任务用的精简流程，例如只跑其中两个阶段；必须保留一个等于完整顺序的 full。见工作流档位
CHECKLIST_OPTIONAL_STAGES可以没有检查项的阶段
VERIFICATION_STAGE_PROFILES每个阶段的验证强度：explore / develop / certify
REQUIRE_INDEPENDENT_REVIEW是否要求独立审查，默认开启
stage_completion_issues(...)用代码检查某阶段是否真的完成，比如文件是否存在

完整约定由 argus/core/vertical_contract.py 检查；想看一个只有 3 个阶段的自带纵向，读 argus/verticals/argus_maintenance/stages.py。

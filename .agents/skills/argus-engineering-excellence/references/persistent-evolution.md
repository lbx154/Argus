# Persistent Skill and Wiki Evolution

## 两类持久资产

每个任务结束后同时检查：

- Skill 是否获得了可迁移的流程、策略、工具用法、决策模式、失败教训或验证方法。
- Wiki 是否获得了事实、概念、项目知识、实验结论、证据、引用或实体关系。

不要机械地把同一内容写入两边。Skill 主要回答“以后如何做”，Wiki 主要回答“已经
知道什么”。使用稳定 ID 和引用关联二者，保持各自唯一事实来源。

结果必须持久化，不能只存在于当前 session、临时摘要或模型上下文。系统重启后仍可
检索，后续任务应能实际发现并使用此前经验。

## 默认有效，不设 Skill 门禁

Skill 的新增和更新默认合格、默认可用。完成后立即版本化和持久化，供后续任务使用。
不要设置 candidate、准入、晋升分数、独立质量分类器或其他 Skill 文本门禁。

Reviewer 不脱离任务抽象评价 Skill 文案，而是审查 Engineer 携带具体 Skill 版本
执行真实任务时产生的完整轨迹：它是否帮助 Engineer 获取信息、形成判断、调用工具、
避免错误、提高效率并完成有价值的工作。

根据真实轨迹和 reviewer 反馈，由 agent 判断后续如何修正、保留、拆分、合并或删除
Skill。harness 只负责持久化、关联、渐进式披露和审计。

## 渐进式披露与结构化存储

默认只加载低成本索引、摘要、适用条件和元数据；确认相关后再展开具体方法、正文、
示例和原始证据。不要把完整 Skill/Wiki 或历史 transcript 无差别注入上下文。

采用结构化存储，至少关联：

- 类型、稳定 ID、版本、来源和适用范围。
- 依赖、摘要、正文位置和证据引用。
- 关联任务、实际加载片段、Engineer 轨迹和 reviewer 反馈。
- 创建、更新时间、使用记录以及废弃或替代关系。

支持检索、去重、冲突表达、更新、废弃和回滚。不要持续堆积无边界 Markdown，也不
要维护多份容易漂移的 Skill 描述。

## 角色可见性

Manager 和 Planner 应能按需查看 Engineer Skill 的能力摘要、适用范围、工具经验、
历史轨迹和 reviewer 反馈，据此拆分任务和选择合适 Engineer，做到知人善任。具体
分工由它们判断，不由 harness 用关键词、标签分数或规则机械匹配。

Engineer 读取当前执行真正需要的内容。Reviewer 必须能看到本次使用的准确 Skill
版本、实际展开片段和对应轨迹，并可按需查看完整 Skill。

不同角色从同一结构化事实来源获得不同视图：

- Manager/Planner 默认读取低成本能力摘要，必要时展开。
- Engineer 读取执行所需方法和知识。
- Reviewer 读取与本次轨迹对应的版本和内容。

## 体现进化前后差异

保留版本关系，并在相同或可比的模型、reasoning effort、预算、工具权限和环境下，
观察任务质量、reviewer 判断、可靠性、token、成本、耗时、知识复用和自主解决能力
的变化。除了原任务，也关注经验在后续真实任务中是否被发现和采用。

诚实展示提升、无变化、波动和回退。“写入更多知识”本身不代表能力提升。对比结果
只为 Manager、Planner、Engineer 和 Reviewer 提供判断证据，不设置机械分数门槛，
也不由 harness 自动决定 Skill 晋升或删除。

严格隔离 benchmark 题目、答案、证明和针对性解法，防止 Skill/Wiki 污染评测。
自进化的目标不是知识无限增长，而是让下一次任务真正利用上一次任务的经验。

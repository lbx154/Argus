# Code Health

## 持续删除技术债

使用调用关系、配置入口、运行 trace、测试和版本历史识别重复、废弃、不可达、
低价值或已被替代的代码。能确认删除就不要只标记 deprecated；同步清理旧配置、
兼容分支、失效 feature flag、残留测试和过时文档。

低使用频率不是充分删除理由。恢复、安全、迁移、审计和反作弊路径可能很少触发但
仍然关键。删除前确认职责已消失或由单一新路径完整承接，删除后验证预期行为。

## 精简测试

盘点每项测试保护的行为、运行时间、失败历史和独有价值。优先删除或合并：

- 重复覆盖同一行为的测试。
- 已删除功能的残留测试。
- 只绑定内部实现、没有外部风险的脆弱断言。
- 低价值快照和可参数化的复制用例。
- 已被更强测试完整覆盖且没有独立故障信号的用例。

不要因“慢”直接删除关键回归、预算、数据完整性、反作弊、安全、持久化和核心执行
路径测试。有价值但昂贵的测试应优化、分层或避免重复执行。区分快速单元测试、
集成测试和端到端测试，让日常反馈更快，同时保留必要的完整验证。

比较清理前后的测试 wall time、稳定性和被保护行为；不要把测试数量或覆盖率数字
本身当作目标。

## 全项目架构治理

以专业软件架构师视角建立可追踪的一方代码清单，分批阅读生产代码、测试、配置、
后端适配器、持久化、调度、CLI 和 UI。记录已审阅范围；未覆盖完整清单前不要声称
“看完全部代码”。

重点识别职责混乱、重复实现、循环依赖、跨层耦合、过度抽象、超大模块、隐式状态、
多事实来源、失效接口、错误依赖方向和历史兼容层。

根据真实调用和运行行为逐步明确模块边界、依赖方向、公共接口、状态所有权和唯一
事实来源。采用小步完整重构，不做大爆炸式重写，也不为了架构美观制造无用抽象。
每次重构删除被替代路径，并展示复杂度或后续开发成本如何下降。

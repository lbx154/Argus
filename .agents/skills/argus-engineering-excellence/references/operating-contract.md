# Operating Contract

## 愿景

把 Argus 建成自主、简洁、可靠、高效、可审计、可持续进化的科研系统。资深
工程师第一次阅读项目时，应能从清晰架构、克制抽象、统一事实来源、高价值测试、
完整预算控制、真实运行证据和专业交互中理解系统，而不是先解开历史补丁。

每项设计都应有存在理由；每层抽象都应降低复杂度；每条测试都应保护真实风险；
每次模型调用都应可追踪、可计费；每项性能和科研结论都应可复现、可审查。

## 权威边界

- Manager 是操作员前门和 pipeline stage 转移权威。
- Planner 基于目标、项目状态和 engineer 能力安排后续工作。
- Engineer 自主调查、实现、运行实验并提交证据。
- Reviewer 阅读实际 artifact、轨迹和所用 Skill，独立判断工作价值与完成状态。
- harness 不用关键词、正则、预设答案或硬编码分数替上述角色做判断。
- 机器硬规则仅用于真实性、预算边界、审计、权限和数据完整性等护栏。

给 agent 真访问与必要工具，让它自行测量、检索、比较和判断。不要由 operator 或
harness 预先算好瓶颈、研究结论或解决方案再喂给 agent。

## 工作节奏

这是持续目标，不是一次大重写。先从真实证据选一个最高价值问题，再完成一个
可独立验证、可回滚、可交付的增量。采用小步重构，但不能用“改动小”作为只修症状、
遗漏入口或保留双实现的借口。

修改前检查当前工作树和并行工作；修改后删除被取代路径，运行针对性验证并保存
证据。不要顺手重写无关模块，也不要为了漂亮数字削弱任务定义。

## 结果表达

报告实际发生的事情，包括提升、无变化、回退、失败和测量限制。涉及公平比较时，
保持硬件、harness、模型、reasoning effort、预算和输入条件可比，并明确无法控制的
差异。

Reviewer 是任务是否完成的事实来源。评测、检查器和统计只向 reviewer 提供证据，
不构成替代 reviewer 的隐藏完成门。
